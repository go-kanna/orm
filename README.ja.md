kanna-orm は、リポジトリのインターフェースの裏側で動くデータベースのコードを生成します。インターフェースと、それが読み取るテーブルごとのスコープ型を宣言すると、kanna-orm は実装を生成し、クエリの絞り込み、並べ替え、ページング、行が参照する先の読み込みの方法ごとに、スコープ型のメソッドも生成します。SQL はリテラルとして生成コードに残り、スキーマと合わないカラムや型で止まるのはリクエストではなく、生成かコンパイルです。

[kanna](https://go-kanna.github.io/ja/) コードジェネレータファミリーの 1 つです。Go 1.26 以上と、pgx か database/sql 経由の PostgreSQL、または database/sql 経由の MySQL 8.4 以上が必要です。

## インストール

```sh
go get -tool github.com/go-kanna/orm/cmd/kanna-orm
```

生成コードは `github.com/go-kanna/orm` のパッケージをインポートします。これは上のコマンドで依存に追加されます。これらのパッケージは標準ライブラリ以外には依存しません。ドライバは自分で用意します。手書きのコードが使うのは次のパッケージです。

| パッケージ     | 用途                                                                                            |
|----------------|-------------------------------------------------------------------------------------------------|
| `orm`          | repository が返すエラー `ErrNotFound` と `ErrRequiredRelation`                                  |
| `orm/scope`    | 手書きで宣言するスコープ型のフィールド `Of`                                                     |
| `orm/relation` | `Select<Field>` と `Preload<Field>` に渡すクロージャが返す・受け取る `Single`、`Many`、`Column` |
| `orm/join`     | 結合した projection の明示的な条件 `On`                                                         |
| `orm/option`   | repository の constructor に渡す option `WithHook`                                              |
| `orm/hook`     | その option に渡す関数の組と、関数が受け取る値 `Hook`、`Query`、`Execution`                     |

`orm/change` の `Set` は、生成される change set の `Of` が返す型で、手書きのコードが名前を書くことはありません。`orm/impl` は生成コードが動く土台で、インポートするのは生成コードだけです。

## 使い方

kanna-orm はスキーマを、マイグレーションではなくデータベースから読み取ります。データベースをマイグレーションし、`describe` でモジュールのルートにスナップショットを書き出します:

```sh
go tool kanna-orm describe -database-url "$DATABASE_URL" ./...
```

`kanna-orm.snapshot.json` はマイグレーションと一緒にコミットします。スキーマの変更がレビューで見えるようになり、生成はスナップショットだけを読むのでデータベースが要りません。

モデルのパッケージを指定すると、kanna-orm は、そのモデルのうち名前に対応するテーブルがあるものそれぞれについて、スコープ型を宣言します:

```go
package scopes

//go:generate go tool kanna-orm

//kanna:scopes ../model
```

さらに、コードの他の部分が依存するリポジトリを宣言します:

```go
package repository

//go:generate go tool kanna-orm -destination ../postgres

//kanna:repository
type OrderRepository interface {
	Get(ctx context.Context, id model.OrderID, s ...scopes.Order) (model.Order, error)
	List(ctx context.Context, s ...scopes.Order) ([]model.Order, error)
	Insert(ctx context.Context, o model.Order) (model.Order, error)
	Delete(ctx context.Context, id model.OrderID) error
}
```

モデルは、ドメインでの形のままです:

```go
package model

type Order struct {
	ID         OrderID
	CustomerID CustomerID
	Status     OrderStatus
	PlacedAt   time.Time
	Memo       *string `orm:"note"`
	Lines      []OrderLine
}
```

`go generate ./...` を実行すると、スコープ型と同じディレクトリに `scopes_gen.go` が書き出されます:

```go
// Code generated by kanna-orm. DO NOT EDIT.

// Orders returns a scope over all the rows of orders.
func Orders() Order { return Order{} }

// StatusNe narrows to the rows whose status is not v.
func (s Order) StatusNe(v model.OrderStatus) Order {
	return Order{s.q.Where(`status <> `, v)}
}

// PlacedAtDesc orders the rows by placed_at, latest first.
func (s Order) PlacedAtDesc() Order {
	return Order{s.q.OrderBy(`placed_at`, true)}
}

// WithLines loads Lines, from order_lines by order_id.
func (s Order) WithLines(sub ...OrderLine) Order {
	// ...
}

// ...a method for each column and relation, and Limit, Offset, Or, Not, After, Before, Cursor, and AfterCursor.
```

`../postgres` には実装が書き出されます:

```go
// Code generated by kanna-orm. DO NOT EDIT.

// OrderRepository implements repository.OrderRepository on PostgreSQL through pgx.
type OrderRepository struct{ db DBTX }

func NewOrderRepository(db DBTX) OrderRepository { return OrderRepository{db: db} }

func (r OrderRepository) Insert(ctx context.Context, o model.Order) (model.Order, error) {
	const q = `INSERT INTO orders (id, customer_id, status, placed_at, note)
VALUES ($1, $2, $3, $4, $5)
RETURNING id, customer_id, status, placed_at, note`
	var row model.Order
	err := r.db.QueryRow(ctx, q, o.ID, o.CustomerID, o.Status, o.PlacedAt, o.Memo).
		Scan(&row.ID, &row.CustomerID, &row.Status, &row.PlacedAt, &row.Memo)
	if err != nil {
		return model.Order{}, fmt.Errorf("insert into orders: %w", err)
	}
	return row, nil
}

// ...
```

呼び出し側はスコープをチェーンします:

```go
orders, err := repo.List(ctx, scopes.Orders().
	StatusNe(model.OrderCanceled).
	PlacedAtGte(lastMonth).
	WithLines().
	PlacedAtDesc().
	Limit(20))
```

スキーマと合わない宣言は、最初にそれに当たるリクエストまで持ち越さず、生成の時点で止まります:

```console
$ go generate ./...
./scopes.go:6:1: error: Order: the snapshot has no table order
  did you mean orders?
../model/order.go:12:1: error: Order.Memo: orders.note may be NULL, which a string cannot hold
  declare it as *string
./order_repository.go:12:2: error: ListByCustomer: orders has no column for the parameter custmerID
  did you mean customerID (customer_id)?
./order_repository.go:14:2: error: GetByStatus: status is not a unique key of orders, so Get cannot return one row
  use List, or add a unique index on orders (status)
```

リポジトリのインターフェースが参照する `scopes.Order` は `//kanna:scopes` が生成するまで存在しないので、初回の実行前にはコンパイルが通りません。それでも実行は止まりません。kanna-orm はこのディレクティブから型を判断するので、`go generate` が 2 つのパッケージをどちらの順で処理しても構いません。コードが生成前のメソッドを呼び出していても構いません。その実行で生成されるメソッドがないと述べるだけのエラーでは、実行は止まりません。

## スナップショット

`describe` はデータベースに接続し、テーブルごとに、カラム（型、NULL になりうるか、identity、serial、AUTO_INCREMENT のカラムのようにデータベースが自分で値を割り当てるか）、主キー、ユニークキー、外部キーを記録します。さらに、引数のパッケージと、引数が指すディレクトリのうちまだパッケージがないもの（初回の生成前のリポジトリの出力先など）にある[手書きのクエリとスコープ](#手書きの-sql)をそれぞれプリペアし、パラメータと結果カラムの型を記録します。`describe` が実行するものは、何も書き込みません。

データベースは `-database-url` で指定したもの、指定がなければ `$DATABASE_URL` です:

- `postgres://user:password@host:5432/database` は pgx 経由の PostgreSQL です。テーブルはカレントスキーマのもので、カレントスキーマは `?search_path=` で選びます。
- `mysql://user:password@host:3306/database` は go-sql-driver/mysql 経由の MySQL で、`?` の後にこのドライバのオプションを指定できます。テーブルは URL で指定したデータベースのものです。

型はデータベース自身が答えたものなので、kanna-orm にはデータベースと食い違う独自の SQL パーサがありません。MySQL はプリペアした文の結果の情報を返さないので、MySQL では `describe` は文を `SELECT t.* FROM (...) AS t LIMIT 0` で包んでカラムを読み取ります。この文は行を返しません。

スナップショットは生成に必要なものだけを記録します。そのため、`describe -check` で分かるのは、コードが現在のスキーマから生成されたことであり、2 つのスキーマが同じであることではありません:

| 記録するもの | 記録しないもの |
|---|---|
| カラムの型（宣言した長さや精度を含む）: `varchar(100)`, `numeric(10,2)` | デフォルト値の内容（デフォルト値があることだけを記録する） |
| カラムが NULL になりうるか、デフォルト値を持つか、データベースが値を割り当てるか | CHECK 制約 |
| 主キー、ユニークキー、外部キー | 部分インデックスの条件 |
| 手書きのクエリごとのパラメータと結果カラムの型 | トリガー、照合順序、コメント |

記録されないものだけを変更するマイグレーションでは、スナップショットは変わりません。それらをレビューしたり、2 つのデータベースを比較したりするには、マイグレーションのツールを使ってください。

スナップショットは 1 行に 1 カラムの JSON で、順序は固定です。そのため、マイグレーションは変更した行として差分に現れます:

```diff
     "orders": {
       "columns": [
         {"name": "id", "type": "uuid", "not_null": true},
         {"name": "customer_id", "type": "uuid", "not_null": true},
         {"name": "status", "type": "text", "not_null": true},
-        {"name": "placed_at", "type": "timestamptz", "not_null": true}
+        {"name": "placed_at", "type": "timestamptz", "not_null": true},
+        {"name": "note", "type": "text"}
       ],
```

モジュールのスナップショットは、ルートにある `kanna-orm.snapshot.json` の 1 つです。生成はパッケージから親ディレクトリをたどってこれを見つけます。2 つのデータベースを使うモジュールは、それぞれを別のファイルに書き出し、両方のコマンドで `-snapshot` を使ってそのファイルを指定します。

CI では、マイグレーションしたばかりのデータベースを `-check` 付きで `describe` します。スナップショットが古い場合は失敗します:

```console
$ go tool kanna-orm describe -check ./...
./kanna-orm.snapshot.json: error: out of date with the database
  orders.note (text) is in the database but not in the snapshot
  run go tool kanna-orm describe to update it
```

## スコープ型

スコープ型は、フィールドが非公開の `scope.Of[M]` だけの構造体です。`M` はテーブルの行を読み込むモデルです。これにより、スコープを絞り込めるのはそのメソッドだけになります。kanna-orm が読み書きするテーブルにはそれぞれスコープ型が 1 つあり、各モデルは 1 つのテーブルに属します。テーブルとモデルを結び付けるのはスコープ型だけです。

`//kanna:scopes` の後にモジュールのパッケージを、インポートパスか、`../model` のようなファイルからの相対パスで指定すると、それらのパッケージの構造体のうち、スナップショットに対応する名前のテーブルがあるものそれぞれについて、`scopes_gen.go` にスコープ型を宣言します。対応するテーブルの名前は、構造体の名前をスネークケースにして最後の単語を複数形にしたもの（`OrderLine` なら `order_lines`、`Category` なら `categories`、`Person` なら `people`）で、それがなければスネークケースのままの名前です。値オブジェクトのように対応するテーブルがない構造体にはスコープ型が宣言されず、中間テーブルのように対応する構造体がないテーブルにも宣言されません。自分のメソッドは、他の型と同じように、パッケージの別のファイルでこの型に書きます。

それ以外の名前のテーブルや独自の名前のスコープ型は、手で宣言します。手で宣言したものは、そのモデルやテーブルについて `//kanna:scopes` が暗黙に宣言するものより優先されます:

```go
//kanna:scope table=people
type Person struct{ q scope.Of[model.Person] }
```

リレーションがたどり着くモデルのうち、どのスコープ型にも指定されていないものがあると、生成が止まります:

```console
../model/order_line.go:9:1: error: OrderLine.Product: no scope type is declared for model.Product
  declare one where products are queried: //kanna:scope table=products
```

kanna-orm は、スコープ型ごとに次のものを生成します:

- `//kanna:scopes` が暗黙に宣言する場合は、型そのもの。
- テーブルにちなんだ名前の、空のスコープを返す関数。`orders` なら `Orders()` です。その名前が型自身の名前と同じ場合や、他で使われている場合は、型を手で宣言し、`//kanna:scope table=person func=People` のように `func=` で別の名前を選んでください。
- カラム、リレーション、[手書きのスコープ](#手書きの-sql)ごとのメソッド。
- `Limit`、`Offset`、`Or`、`Not`、`After`、`Before`、`Cursor`、`AfterCursor`。

どのメソッドも新しいスコープを返し、レシーバは変更しません。そのため、途中まで組み立てたスコープを共有できます。`base.Limit(10)` と `base.Limit(20)` は互いの limit に影響しません。ゼロ値の `Order{}` も空のスコープです。

### カラムとフィールド

フィールドは、フィールド名をスネークケースにした名前のカラムを保持します。`CustomerID` は `customer_id` を、`PlacedAt` は `placed_at` を保持します。この変換は機械的なので、それ以外の名前のカラムを保持するフィールドは、タグでそのことを示します:

| タグ | 意味 |
|---|---|
| *（なし）* | フィールド名をスネークケースにした名前のカラム |
| `orm:"note"` | カラム `note` |
| `orm:"note,nullzero"` | nullable な文字列カラム。NULL をゼロ値へ読み込み、ゼロ値は NULL として書き込む |
| `orm:",default"` | 生成する INSERT からカラムを省略し、DB のデフォルト値を使う |
| `orm:"-"` | カラムではない。kanna-orm はこのフィールドを読み書きしない |
| `orm:"fk=order_id"` | [リレーション](#リレーション)で、候補が複数あるときにたどる外部キー |
| `orm:"fk=order_lines.order_id"` | 同上。カラムだけでは特定できない場合のために、テーブルも指定する |

カラムのないフィールド、nil になれないフィールドが保持する NULL になりうるカラム、そして insert されるテーブルで、データベースが値を必須とするのにモデルにフィールドがないカラムは、いずれも生成を止めます。それ以外の場合、モデルにフィールドがないカラムには何もしません。

nullable な文字列の欠落をフィールドのゼロ値で表す場合は `nullzero` を指定できます。`sql.Scanner` を実装した enum などの名前付き文字列型にも対応します。生成コードは `sql.Null[T]` を使うため、NULL を enum 自身の非 NULL 用 Scan へ渡さず、非 NULL の値は引き続きその Scan で検証します。テーブル操作と手書きクエリのモデルの両方に適用されます。フィールド名の snake case がカラム名と一致する場合、`orm:",nullzero"` とカラム名を省略できます。

[PostgreSQL](example/postgres/model/model.go) と [MySQL](example/mysql/model/model.go) の example では、任意の注文メモに使っています。

```go
Memo string `orm:"note,nullzero"`
```

[readMemos](example/postgres/memos.go) では `MemoIsNull()` で検索し、空のメモが SQL NULL として保存され、空文字として読み込まれることと、空でないメモが保持されることを確認します。ここでは `Memo` を `note` カラムに対応させるため明示しています。フィールド名が `Note` なら `orm:",nullzero"` だけで十分です。

フィールドの型は、ドライバがカラムの型を読み込める型でなければなりません。`bigint` には整数型、`text` には string、`timestamptz` や `datetime` には `time.Time`、`bytea` や `blob` には `[]byte`、`uuid` には Go 1.27 の `uuid.UUID` か string、PostgreSQL の配列にはそれらのスライスです（MySQL に配列はありません）。`Scan` メソッドと `Value` メソッドを持つ型は自分で変換するので、どのカラムにも使えます。enum や `json` のように kanna-orm が知らないデータベースの型については、フィールドの型をそのまま信用します。

カラムから読み込むフィールドは、カラムが持ちうるすべての値も保持できなければなりません。フィールドの範囲を超える値を持つ行はスキャンに失敗し、`float8` や `double` から読み込んだ `float32` は黙って精度を失います。そのため、整数フィールドの幅はカラム以上にします。`bigint` には `int64`、`integer` には `int32` です。符号付きのカラムには符号付きの型を、符号なしのカラムには符号なしの型か少し幅の広い型を使います。`bigint unsigned` には `uint64`、`int unsigned` には `int64` です。`int` と `uint` は、amd64 と同じく 64 ビット幅として扱います。書き込みには、このような幅は必要ありません。データベースは、カラムの範囲を超える値を別の値にして保存せず、拒否するからです。そのため、`integer` に対する `int` のようにカラムより幅の広いフィールドでも問題なく、パラメータの幅も問いません。`numeric` の範囲は記録されないので、どの数値型でも読み込めます。

### カラムのメソッド

メソッドの名前はフィールドから決まるので、`Memo` が保持するカラム `note` からは `MemoContains` ができます。各カラムには、その型で使えるメソッドが生成されます:

| カラム | メソッド（フィールド `Status` の場合） |
|---|---|
| すべて | `StatusEq`, `StatusNe`, `StatusIn`, `StatusNotIn`, `StatusAsc`, `StatusDesc` |
| 順序のある型（数値、時刻、文字列） | 加えて `StatusLt`, `StatusLte`, `StatusGt`, `StatusGte`, `StatusBetween` |
| 文字列 | 加えて `StatusLike`、`%` と `_` をエスケープする `StatusHasPrefix` と `StatusContains`、PostgreSQL では `StatusILike` |
| NULL になりうる | 加えて `StatusIsNull`, `StatusIsNotNull` |

メソッドはフィールドの型を受け取ります。`StatusEq` は `model.OrderStatus` を受け取り、値オブジェクトは、database/sql が送るのと同じように `Value` メソッドを通してデータベースに渡ります。パターンで照合するメソッドは string を受け取ります。パターンはその型の値でなくてよいからです。`[]byte` 以外のスライスで保持されるカラム、つまり配列には、`In` も `NotIn` もありません。NULL になりうるカラムの比較メソッドは、ポインタではなく値を受け取ります。何にもマッチしない `= NULL` を書けないようにするためです。そう書いて表したかったことは `StatusIsNull` で表せます。

### 独自のスコープ

名前を付けたスコープは、生成されたメソッドを使ってスコープ型に自分で書くメソッドです。生成されたメソッドと同じようにチェーンできます:

```go
// Open narrows to the orders that are not canceled.
func (s Order) Open() Order {
	return s.StatusNe(model.OrderCanceled)
}

// Recent orders by placed_at, latest first, and keeps the first n.
func (s Order) Recent(n int) Order {
	return s.PlacedAtDesc().Limit(n)
}
```

検索では、条件を 1 つずつ加えてスコープを絞り込みます:

```go
s := scopes.Orders().Open().Recent(in.PageSize)
if in.CustomerID != nil {
	s = s.CustomerIDEq(*in.CustomerID)
}
if in.Keyword != "" {
	s = s.MemoContains(in.Keyword)
}
orders, err := repo.List(ctx, s)
```

kanna-orm が生成するメソッドと同じ名前のメソッドを自分で書いている場合は、上書きせずに生成を止めます。

### Or と Not

`Or` は、渡したスコープのいずれかにマッチする行にマッチします。各スコープ自身の条件は、すべて同時に成り立つ必要があります:

```go
// WHERE ... AND ((status = $1) OR (placed_at < $2))
s := scopes.Orders().Or(
	scopes.Orders().StatusEq(model.OrderPending),
	scopes.Orders().PlacedAtLt(cutoff),
)
```

`Not` は、渡したスコープにマッチしない行にマッチします。`Or` や `Not` に渡すスコープは条件だけを持ちます。並び順、limit、読み込むリレーションを持つスコープを渡すと、クエリはエラーを返します。どの選択肢も 1 つのカラムの値である場合は、`StatusIn` のほうが同じことを簡潔に表せます。

### リレーション

別のモデル、そのポインタ、またはそのスライスを保持するフィールドはリレーションです。kanna-orm はスナップショットの外部キーからリレーションの種類を判断するので、他に何も書く必要はありません:

| フィールド | 外部キー | 種類 |
|---|---|---|
| `Lines []OrderLine` | `orders` への `order_lines.order_id` | has many |
| `Customer *Customer` | `customers` への `orders.customer_id` | belongs to |
| `Profile *Profile` | `users` への `profiles.user_id`（ユニークキー） | has one |
| `Tags []Tag` | `user_tags` のような、両方への外部キーを持つテーブルを経由 | many to many |

使える外部キーが複数ある場合は、生成が止まり、タグを求められます:

```console
../model/order.go:16:1: error: Order.Lines: order_lines has two foreign keys to orders (order_id, replaced_order_id)
  order_lines.order_id to orders
  order_lines.replaced_order_id to orders
  tag the field with the one to follow: orm:"fk=order_id"
```

両方への外部キーを持つテーブルは、関連先のテーブルの外部キーと同じように数えられます。`refunds` が `orders` と `order_lines` を参照している場合、`Lines` は注文の明細とも返金された明細とも解釈できるので、やはりタグが求められます。ここでの `order_id` のようにカラムだけでは特定できない場合は、タグでテーブルも `orm:"fk=order_lines.order_id"` のように指定します。

リレーションは、スコープが `With` メソッドで要求したときにだけ読み込まれます。`With` メソッドは関連する行のスコープを受け取り、その条件、並び順、さらに読み込むリレーションを指定できます。

```go
o, err := repo.Get(ctx, id, scopes.Orders().
	WithCustomer().
	WithLines(scopes.OrderLines().
		QuantityGt(0).
		SKUAsc().
		WithProduct()))
```

PostgreSQL では、リレーションのクエリは、行がいくつあってもリレーションごとに 1 回です。上の呼び出しは、注文、顧客、注文の明細、商品に 1 回ずつ、計 4 回のクエリを実行します。中間テーブルを経由するリレーションは 2 回で、中間テーブルのキーの組に 1 回、関連する行に 1 回です。関連する行は、すでに読み込んだ行のキーを使い、同じキーは 1 度だけ指定して読み込みます。PostgreSQL では `= ANY($1)` を、MySQL では `IN (?, ...)` を使い、MySQL ではキーを 1000 個ずつ、それぞれ別のクエリで送ります。1 つの行に関連する行はすべて 1 つのクエリで読み込まれ、渡したスコープの順序で並びます。

- 読み込まれたスライスは決して nil になりません。関連する行がなければ空になります。nil のスライスは読み込まれていません。
- ポインタは、読み込まれていないときも関連する行がないときも nil です。この 2 つを区別するには、モデルに kanna-orm の型を持ち込むことになります。
- 関連する行に対する limit や offset は、行ごとではなく関連する行全体を数えてしまうので、limit や offset を持つスコープを `With` メソッドに渡すと、クエリはエラーを返します。行ごとに先頭の数件を読み込むには、[`Preload<Field>`](#親カラムを参照する単一値の取得と親ごとの関連取得) を使ってください。
- リレーションは読み込むだけで、決して書き込みません。`Insert` と `Update` が書き込むのはその行自身のカラムで、読み戻した行もそれらのカラムだけを保持します。
- 複数カラムの外部キーによるリレーションは、それらのカラムを行として扱って読み込みます。PostgreSQL では `(a, b) IN (SELECT * FROM unnest($1, $2))`、MySQL では `(a, b) IN ((?, ?), ...)` です。

### ページング

`Limit` と `Offset` は SQL と同じようにページングします。行が増減してもずれないページにするには、ページの最後の行を `After` に渡します。スコープの順序でその続きから読み込みます:

```go
s := scopes.Orders().Open().PlacedAtDesc().Limit(20)

page, err := repo.List(ctx, s)
// ...
next, err := repo.List(ctx, s.After(page[len(page)-1]))
// WHERE status <> $1 AND (placed_at, id) < ($2, $3)
// ORDER BY placed_at DESC, id DESC LIMIT 20
```

- 順序が主キーで終わっていない場合は、`After` と `Before` が主キーを追加するので、順序の上で等しい行にも 1 つの順序が付きます。主キーがないと、等しい行の途中で終わるページでは、その一部が黙って重複したり抜けたりします。
- 順序のすべてのカラムが同じ方向なら、条件は上の例のように行の比較になります。そうでない場合と MySQL では、`a < $1 OR (a = $1 AND b < $2)` のように展開して書かれます。
- `Before` は逆方向に進み、渡した行が先頭にあるページの 1 つ前のページに移動します。リポジトリはそのページを末尾から読み込み、行をスコープの順序に戻して返します。
- NULL になりうるカラムで並べると、行の続きを読み込むクエリはエラーを返し、`Cursor` も同様にエラーを返します。データベースによって NULL の並ぶ位置が異なるからです。

位置をクライアントに渡すには、`Cursor` で文字列にエンコードし、`AfterCursor` でスコープにデコードします:

```go
s, err := scopes.Orders().Open().PlacedAtDesc().AfterCursor(req.PageToken)
if err != nil {
	return nil, err
}
page, err := h.orders.List(ctx, s.Limit(20))
// ...
res.NextPageToken, err = s.Cursor(page[len(page)-1])
```

カーソルは、作成時の順序と、その順序における行の値を JSON として保持します。空のカーソルは先頭を表し、別の順序で作成したカーソルはエラーになります。各値はその型を通してデコードされるので、値オブジェクトはルールをチェックします。クライアントがカーソルを改変しても、変わるのはページの開始位置だけです。

## リポジトリ

`//kanna:repository` を付けたインターフェースは、データベースより上のコードがデータベースに対して何をしてよいかを宣言します。そのパッケージで `kanna-orm -destination <dir>` を実行すると、そのディレクトリの `repository_gen.go` に実装の構造体、そのコンストラクタ、実行の土台となる `DBTX`（sqlc と同じ名前）が書き出されます。

### 同じパッケージに実装する

`-destination .` を指定すると、インターフェースと生成実装を同じパッケージに置けます。インターフェースは公開する必要があります。`Category` なら、非公開の `category`、`newCategory(db DBTX) *category` コンストラクタ、ポインタレシーバーのメソッドを生成します。`NewCategory` を自分で宣言していなければ、`NewCategory(db DBTX) Category` も生成します。スコープのメソッドは `scopes_gen.go` に出力されます。スコープ型は別のパッケージに置いてください。

`Bind(db DBTX) Category` を宣言すると、トランザクションへの接続も生成します。引数には、DBTX を実装した具体的な接続・トランザクションの型や、引数なしの `DBTX()` メソッドでそれを返す型も指定できます。たとえば `Bind(tx tx.Tx) Category` です。Bind は指定された接続を使う新しい実装を返し、元の実装は変更しません。引数は選択したドライバの DBTX に適合し、戻り値はリポジトリ自身のインターフェースである必要があります。手書きの `Bind` があれば、その実装を維持します。

DI に具体的な引数型を渡すには、`-constructor-db` で公開コンストラクタの引数型を指定します:

```go
//go:generate go tool kanna-orm -destination . -constructor-db "*example.com/app/db.Reader"
```

これで `NewCategory(db *db.Reader) Category` が生成され、Bind では引き続きトランザクションの DBTX を使えます。フラグには公開型の完全なインポートパスと名前を指定し、必要なら先頭に `*` を付けます。生成器がそのパッケージを読み込み、選択したドライバの DBTX を実装しているか検証します。同一パッケージへの生成に限り指定できます。コンストラクタや Bind を手書きでラップする必要はありません。

アプリケーション固有のメソッドは、生成される型に直接書けます。`Bind` 以外で、認識できる動詞も手書きのクエリもないメソッドは、手書きの実装に任せます。認識できる動詞か手書きのクエリがあるメソッドを自分で実装した場合は、データベースの処理を非公開のヘルパーとして生成します。手書きの `Upsert` から `r.upsert` を呼び、そのエラーを変換できます。ヘルパーは、パッケージがそれを呼んでいるときだけ生成するので、自分で SQL を実行するメソッドには生成しません。

このヘルパーの生成は同一パッケージへの出力に限ります。ヘルパーのシグネチャはインターフェースのメソッドと同じで、`//kanna:conflict` と `//kanna:lock` も引き継ぎます。ヘルパーと同じ名前のメソッドがすでにあれば、生成を止めます。手書きのクエリは出力先の `.sql` ファイルに置きます。同一パッケージへの出力なら、インターフェースと同じディレクトリです。

```go
//go:generate go tool kanna-orm -destination .

//kanna:repository table=categories
type Category interface {
	Bind(db DBTX) Category
	Upsert(ctx context.Context, c model.Category) error
}

func (r *category) Upsert(ctx context.Context, c model.Category) error {
	return translateError(r.upsert(ctx, c))
}
```

### エラーの変換

[PostgreSQL](example/postgres) と [MySQL](example/mysql) の example では、注文が見つからないエラーを `model.ErrOrderNotFound` へ変換します。repository に `//kanna:repository errors=translateOrderError` を指定し、実装パッケージの [store/errors.go](example/postgres/store/errors.go) に関数を置きます。

```go
func translateOrderError(op orderRepositoryOperation, err error) error {
    if op == orderRepositoryOperationGet && errors.Is(err, orm.ErrNotFound) {
        return model.ErrOrderNotFound
    }
    return err
}
```

非公開の文字列型 `orderRepositoryOperation` と、`orderRepositoryOperationGet`、`orderRepositoryOperationInsert` など、エラーを返す生成メソッドごとの型付き定数を生成します。`Bind` は含みません。example の main では、注文 99 の `Get` が `model.ErrOrderNotFound` を返すことを確認します。変換を指定しない repository は引き続き `orm.ErrNotFound` を返します。

関数の存在と `func(orderRepositoryOperation, error) error` という型を生成時に検証します。操作型がまだ存在しない初回生成にも対応します。生成名と手書きの宣言が衝突した場合はエラーです。エラーに文脈を付けた後、nil でない場合に一度だけ変換します。手書き SQL と関連の読み込みで発生したエラーも対象です。生成された private helper は元のインターフェースのメソッドに対応する操作定数を渡します。手書きメソッド本体には自動適用しません。`errors=` がなければ操作型や変換処理は生成しません。変換しないエラーはそのまま返し、エラーチェーンを保持してください。

### 別のパッケージに実装する

`-destination ../postgres` のように別のパッケージを指定すると、インターフェースと同じ名前の公開構造体、値を返すコンストラクタ、値レシーバーのメソッドを生成します。その構造体に手書きしたメソッドは生成対象から外し、ヘルパーも生成しません。

```go
// DBTX is what the repositories run on: *pgxpool.Pool, *pgx.Conn, or pgx.Tx.
type DBTX interface {
	Exec(ctx context.Context, sql string, args ...any) (pgconn.CommandTag, error)
	Query(ctx context.Context, sql string, args ...any) (pgx.Rows, error)
	QueryRow(ctx context.Context, sql string, args ...any) pgx.Row
}

func NewOrderRepository(db DBTX) OrderRepository
```

トランザクションは、kanna-orm がない場合と同じように開始してコミットします。コンストラクタに `pgx.Tx` か `*sql.Tx` を渡してください。

### メソッド

メソッドの動作は、名前の先頭の動詞で決まります。動詞の後ろは自由に決められます。残りはパラメータで決まります。モデル型のパラメータは書き込む行、スコープは読み込み方を表し、それ以外のパラメータは同じ名前のカラムを指して、そのカラムの値がパラメータと等しい行が対象になります。

| 動詞 | 宣言 | 動作 |
|---|---|---|
| `Get` | `Get(ctx, id model.OrderID, s ...scopes.Order) (model.Order, error)` | パラメータで指定したキーの行を読み込む。なければ `orm.ErrNotFound` を返す |
| `Find` | `Find(ctx, id model.OrderID, s ...scopes.Order) (*model.Order, error)` | 一意キーで任意の行を読み込む。なければ `nil, nil` を返す |
| `First` | `First(ctx, s ...scopes.Order) (model.Order, error)` | スコープにマッチする最初の行を読み込む。なければ `orm.ErrNotFound` を返す |
| `List` | `List(ctx, s ...scopes.Order) ([]model.Order, error)` | スコープにマッチするすべての行を読み込む |
| `Count` | `Count(ctx, s ...scopes.Order) (int64, error)` | スコープにマッチする行を数える |
| `Exists` | `Exists(ctx, s ...scopes.Order) (bool, error)` | マッチする行があるかどうかを返す |
| `Insert` | `Insert(ctx, o model.Order) (model.Order, error)`、または `error` のみを返す形 | 行を 1 つ、または[複数](#複数行の書き込み)書き込む |
| `Update` | `Update(ctx, o model.Order) error` | キー以外のすべてのカラムを書き込む。そのキーの行がなければ `orm.ErrNotFound` を返す |
| `Upsert` | `Upsert(ctx, o model.Order) error` | 行を insert するか、同じキー、または[別のユニークキー](#upsert)を持つ行を update する |
| `Delete` | `Delete(ctx, id model.OrderID) error`、または `Delete(ctx, s ...scopes.Order) (int64, error)` | そのキーの行、またはスコープにマッチする行を削除する |

`Get` は行の存在を必須とし、なければ `orm.ErrNotFound` を返します。`Find` はポインタを返し、不在は `nil, nil`、DB エラーは `nil, err` になります。どちらも主キーまたはユニークキーを満たすキー引数が必要です。追加のスコープで条件を絞り、関連を読み込めます。複数行の候補から一つ選ぶ場合は `First` を使います。結果の構造体へのポインタを返す `Find...` は、同じ不在時の契約を保ったまま手書き SQL でも実装できます。

repository のメソッドに `//kanna:pluck customer_id` を付けると、1 カラムだけを型付きスライスで取得します。たとえば `CustomerIDs(ctx context.Context, s ...scopes.Order) ([]int64, error)` と宣言し、メソッド名は自由に選べます。条件・並び順・件数制限・オフセット・カーソルは `List` と同様に使えます。関連は読み込まず、重複値は保持します。該当行がなければ空のスライスを返します。カラムと戻り値の型を生成時に検証します。NULL を許すカラムには nullable な要素型が必要ですが、モデルの `nullzero` フィールドと同じ型ならゼロ値に変換します。手書き SQL・`conflict`・`lock` との併用は生成エラーです。

```go
//kanna:pluck name
Names(ctx context.Context, s ...scopes.Product) ([]string, error)
```

```go
names, err := products.Names(ctx, scopes.Products().PriceLt(2000).PriceAsc())
```

両 DB の example では、このメソッドで価格を絞った商品名を取得し、モデル全体を読み込まずに値の一覧を返します。



```go
// customerID is customer_id: the orders of one customer.
ListByCustomer(ctx context.Context, customerID model.CustomerID, s ...scopes.Order) ([]model.Order, error)

// number is a unique key of orders, so Get reads one row by it.
GetByNumber(ctx context.Context, number model.OrderNumber) (model.Order, error)

// The key of order_lines is (order_id, sku), so Get takes both.
GetLine(ctx context.Context, orderID model.OrderID, sku model.SKU) (model.OrderLine, error)
```

- 対象のテーブルは、スコープ型がメソッドのモデルを保持するテーブルです。そのため、1 つのインターフェースで集約のすべてのテーブルを読み書きできます。
- 複数のスコープは、チェーンした場合と同じくすべてが同時に適用されます。
- `Get` は、パラメータが主キーかユニークキーのカラムをすべて与えていない限り、生成を止めます。
- `Count` と `Exists` は、スコープの条件だけを使います。並び順、limit、読み込むリレーションを持つスコープを渡すと、それらを無視せずにエラーを返します。
- スコープを渡しても条件がない `Delete` は、すべての行を削除せずにエラーを返します。
- `error` だけを返す `Delete` は、`Update` と同じく、1 行も削除しなかったときに `orm.ErrNotFound` を返します。`(int64, error)` を返す `Delete` は削除した行数を返します。0 行の場合も同じです。
- メソッドと同じ名前の[手書きのクエリ](#手書きの-sql)があれば、動詞の代わりにそれが使われます。動詞も手書きのクエリもないメソッドは生成を止めます。
- 生成された構造体のメソッドを自分で書いた場合、その実装は手書きのファイルに残ります。[同じパッケージへの出力](#同じパッケージに実装する)で、認識できる動詞か手書きのクエリがある場合は、非公開のヘルパーも生成します。別のパッケージへの出力では、そのメソッドを生成対象から外します。

メソッドのモデルは、戻り値、書き込む行、スコープから決まり、それらがなければ `model.OrderID` のようにモデルと一緒に宣言された型のキーから決まります。`uuid.UUID` や `int64` のような他の型のキーしか受け取らないメソッドからはモデルが決まらず、インターフェースが `table=` でテーブルを指定しない限り、生成を止めます:

```go
//kanna:repository table=todos
type TodoRepository interface {
	Get(ctx context.Context, id uuid.UUID) (model.Todo, error) // todos, by its result
	Delete(ctx context.Context, id uuid.UUID) error            // todos, by table=
}
```

`table=` は、モデルが決まらないメソッドのテーブルであり、それ以外には適用されません。自分のモデルが決まるメソッドはそのテーブルを読み書きするので、集約のインターフェースは引き続き集約の各テーブルに届きます。

`orm.ErrNotFound` は、見つからなかったものの情報でラップされて返るので、`errors.Is` で判定し、リポジトリを呼び出す箇所でアプリケーションのエラーに変換してください。

### uuid をキーにする

Go 1.27 以降では、`uuid` カラムは標準ライブラリの `uuid.UUID` で保持します。pgx と database/sql はこの型をそのまま読み書きします。それより前のバージョンでは、string か、`Scan` メソッドと `Value` メソッドを持つ独自の型で保持します。uuid をキーにするテーブルの宣言は、`table=` を除いて他のテーブルと同じです:

```go
type Todo struct {
	ID    uuid.UUID
	Title string
}

//kanna:repository table=todos
type TodoRepository interface {
	Get(ctx context.Context, id uuid.UUID) (model.Todo, error)
	List(ctx context.Context, s ...scopes.Todo) ([]model.Todo, error)
	Upsert(ctx context.Context, t model.Todo) error
	Delete(ctx context.Context, id uuid.UUID) error
}
```

- `uuid.UUID` はモデルと一緒に宣言された型ではないので、これしか受け取らないメソッドからはテーブルが決まりません。`Delete` のテーブルは `table=` から決まり、`Get` のテーブルは戻り値から決まります。
- uuid には比較できる順序がないので、そのカラムには `Eq`、`Ne`、`In`、`NotIn`、`Asc`、`Desc` は生成されますが、`Lt` も `Between` も生成されません。それでもページは uuid を基準に行の続きから読み込めて、カーソルは uuid をテキストとして保持します。
- デフォルトが `uuidv7()` のカラムを、自動採番の対象として自動判定はしません。`orm:",default"` がなければ、insert はゼロの UUID もそのまま書き込みます。Go 側で `uuid.NewV7()` を使って ID を与えるか、フィールドに `orm:",default"` を指定して DB のデフォルト値を使ってください。
- MySQL に `uuid` 型はなく、kanna-orm は `binary(16)` や `char(36)` に対する `uuid.UUID` を受け付けません。`[]byte`、string、`Scan` メソッドと `Value` メソッドを持つ独自の型のいずれかで保持してください。

[go-kanna/showcase](https://github.com/go-kanna/showcase) は、to-do を `uuid.UUID` をキーにして管理する to-do サービスです。

### スカラーのリレーション

関連する行の 1 カラムを、enum を含むスライスへ直接読み込めます。関連先のテーブルとカラムを指定し、中間のモデルやスコープ型は不要です。

```go
type Device struct {
    ID uuid.UUID
    Topics []Topic `orm:"relation=device_topics,column=topic"`
}
```

スナップショットに `device_topics` から `devices` への外部キーが必要です。参照先のカラムは親モデルが保持している必要があります。複数の外部キーがある場合は `orm:"relation=device_topics,column=topic,fk=device_id"` で選択します。カラムの型と NULL の許容をスライスの要素型に照合します。

複合外部キーにも対応します。例えば `order_tags.(tenant_id, order_id)` から `orders.(tenant_id, id)` への関連は、組全体で検索し、親ごとに振り分けます。親モデルは参照先の両カラムを保持する必要があります。組を条件にしてバッチで読み込むため、別テナントで同じ ID があっても混在しません。キーのいずれかのポインタが nil の親は、関連の読み込み対象から外れます。

生成されたスコープには `WithTopics()` が追加されます。通常生成の検索で指定した場合だけ、関連する値をバッチで読み込み、選択したカラムの昇順で格納します。enum の値は Scanner を通ります。読み込んだ関連が 0 件なら空のスライス、指定しなかった関連は nil です。親の INSERT・UPDATE と手書き SQL のモデルマッピングからは除外します。関連の更新処理は別に実装してください。

```go
device, err := devices.GetByToken(ctx, platform, token, scopes.Devices().WithTopics())
```

### 書き込み

行は、モデルが保持するとおりに書き込まれます。データベースが自分で値を割り当てるカラム（identity、serial、AUTO_INCREMENT）と、明示的に `default` を指定したフィールドは INSERT から除外します。それ以外のゼロ値はそのまま書き込み、デフォルトが `true` のカラムに対する `false` も `false` のままです。`created_at` と `updated_at` はドメインで設定するか、明示的に DB のデフォルト値を使ってください。

モデルを返す `Insert` は、データベースが保存した行を読み戻します。`error` だけを返す `Insert` は書き込むだけです。MySQL では、データベースが主キーを割り当てる場合は `LAST_INSERT_ID()` で、そうでなければ主キーで読み戻します。MySQL が数えるのは `Update` が変更した行で、見つけた行ではありません。そのため、1 行も変更されなかった場合、kanna-orm は行が存在するかを確認してから `orm.ErrNotFound` を返します。

### DB のデフォルト値

`orm:",default"` を指定したフィールドは、生成する INSERT のカラムから常に省略します。カラム名が異なる場合は `orm:"created_at,default"` のように指定できます。スナップショットに DB の DEFAULT または自動採番の情報がないカラムは生成エラーになります。`default` と `nullzero` は併用できます。

```go
type Product struct {
    SKU      SKU
    Name     string
    Price    int64
    Currency string `orm:",default"`
}
```

[PostgreSQL](example/postgres) と [MySQL](example/mysql) の example では、`products.currency` に `DEFAULT 'JPY'` を定義しています。モデルに `Currency: "USD"` を渡しても INSERT では省略され、DB に保存された値が `JPY` であることを読み戻して確認します。タグがないフィールドは従来どおりゼロ値も書き込みます。一括 INSERT と Upsert にも適用し、手書き SQL は変更しません。

PostgreSQL では、モデルを返すメソッドが RETURNING で DB の値を読み戻します。例えば `ID uuid.UUID` に `orm:",default"` を指定すると、Go 側で採番せず `DEFAULT uuidv7()` の主キーを使えます。全カラムを省略する単一行の INSERT は DEFAULT VALUES を使います。一括書き込みには、少なくとも一つ入力カラムが必要です。

UPDATE では、タグを指定した非キーのフィールドもモデルの値を書き込みます。Upsert は競合時に、タグを指定したカラムの保存済みの値を DB のデフォルト値に戻さずに保持します。`keep=` を指定する必要はありません。`updated_at` のようなカラムも競合時に更新しないので、トリガーで代入してください。

**MySQL の制約:** RETURNING の代替処理や、一意キーを自動で探す処理は追加しません。従来の AUTO_INCREMENT、入力済みの主キー、Upsert に明示した競合キーによる読み戻しを使います。`default` がその読み戻しに必要なキーを省略する場合、モデルを返すメソッドは生成エラーになります。`error` のみを返すメソッドは読み戻しが不要なので省略できます。一括書き込みからモデルを返せない既存の制約も維持します。

### INSERT の競合を無視する

`//kanna:insert` を付けると、`Use` のようなドメインに合わせたメソッド名でも INSERT を生成できます。このディレクティブは引数を取らず、手書き SQL や `//kanna:pluck` とは併用できません。

PostgreSQL では、Insert の `//kanna:conflict` に `do=nothing` を指定できます。カラムには主キーまたはユニークキーを指定します。そのキーでの競合だけを無視し、それ以外の制約違反はエラーを返します。

```go
//kanna:insert
//kanna:conflict token_hash do=nothing
Use(ctx context.Context, token model.UsedIDToken) (int64, error)
```

戻り値は挿入件数で、新しいトークンなら 1、既存のトークンなら 0 です。`error` のみを返すメソッドは、競合を無視した場合も成功します。モデルを返すメソッドは RETURNING を使い、競合で挿入されなければ `orm.ErrNotFound` を返します。一括 INSERT は挿入件数または新しく挿入した行のスライスを返せます。既存の行は結果に含めません。

`do=nothing` は `keep=`・`coalesce=` と併用できず、Upsert にも指定できません。MySQL では生成エラーになります。`INSERT IGNORE` は指定したキーだけに競合処理を限定できず、無関係なエラーも抑制するためです。通常の単一行 Insert も `(int64, error)` で挿入件数を返せます。

### Upsert

`Upsert` は、主キーで既存の行と突き合わせます。別のユニークキーで突き合わせるには、`//kanna:conflict` でそのカラムを指定し、`keep=` で変更しないカラムを指定します:

```go
//kanna:repository
type UserRepository interface {
	// UpsertByEmail meets the user of a tenant by their email address.
	//kanna:conflict tenant_id,email keep=created_at
	UpsertByEmail(ctx context.Context, u model.User) (model.User, error)
}
```

```sql
-- PostgreSQL
INSERT INTO users (tenant_id, email, name, created_at)
VALUES ($1, $2, $3, $4)
ON CONFLICT (tenant_id, email) DO UPDATE SET name = EXCLUDED.name
RETURNING id, tenant_id, email, name, created_at

-- MySQL, which then reads back by LAST_INSERT_ID() the row inserted or updated
INSERT INTO users (tenant_id, email, name, created_at)
VALUES (?, ?, ?, ?) AS new
ON DUPLICATE KEY UPDATE id = LAST_INSERT_ID(id), name = new.name
```

カラムはテーブルの主キーかユニークキーと完全に一致しなければならず、データベースが値を割り当てるカラムは含められません。insert はそのカラムの値を渡さないので、行を突き合わせる材料にならないからです。突き合わせた行では、そのキーのカラム、主キー、`keep=` で指定したカラムを除くすべてのカラムを更新します。更新するカラムが残らない場合は、キーに自分自身を設定するので、行はやはり読み戻されます。MySQL はどのユニークキーの競合でも更新するので、指定したキー以外のユニークキーを持つテーブルには警告が出ます:

```console
./user_repository.go:14:2: warning: UpsertByEmail: on MySQL, a conflict on (tenant_id, login) also updates the row
  users has unique keys other than (tenant_id, email)
```

`coalesce=` を指定すると、入力の SQL 値が NULL の場合だけ既存値を保持します。

```go
//kanna:conflict email keep=created_at coalesce=phone
UpsertByEmail(ctx context.Context, c model.Customer) (model.Customer, error)
```

example の `CustomerRepository` は `Customer.Phone` に使っています。非 nil の電話番号なら更新し、nil なら既存値を保持します。`keep=created_at` は常に登録日時を保持します。二つのオプションの順序は自由です。COALESCE が扱うのは SQL NULL で、空文字や数値の 0 自体は対象になりません。文字列フィールドに `nullzero` を指定した場合、空文字を SQL NULL として扱います。キー、`keep=` の対象、存在しないカラムなど、実際に更新しないカラムへの `coalesce=` は生成エラーです。

```sql
-- PostgreSQL
phone = COALESCE(EXCLUDED.phone, customers.phone)

-- MySQL
phone = COALESCE(new.phone, customers.phone)
```

### 複数行の書き込み

スライスを渡した `Insert` や `Upsert` は、その中のすべての行を書き込みます:

```go
InsertLines(ctx context.Context, lines []model.OrderLine) error
```

```sql
-- PostgreSQL: one statement, however many rows
INSERT INTO order_lines (order_id, sku, quantity)
SELECT * FROM unnest($1::uuid[], $2::text[], $3::int[])
```

- PostgreSQL では、戻り値が `([]model.OrderLine, error)` なら `RETURNING` で行を読み戻します。
- MySQL では、行を `VALUES (?, ?, ?), (?, ?, ?), ...` で送り、1 つの文に入るプレースホルダの数を超える場合は複数の文に分割します。すべて成功するかすべて失敗するかにしたい場合は、コンストラクタにトランザクションを渡してください。
- MySQL には `RETURNING` がないので、MySQL では `error` だけを返す形以外は生成を止めます。
- PostgreSQL は、2 つの行が同じキーを持つ upsert を拒否します。
- `unnest` は配列の配列を平坦にするので、PostgreSQL では配列カラムを持つテーブルは生成を止めます。行を 1 つずつ書き込んでください。

### 行ロック

`//kanna:lock` を付けた `Get`、`Find`、`First`、`List` は、読んだ行をトランザクションが終わるまでロックします。読んだ内容が、書き戻す時点でも変わっていないようにするためです:

```go
//kanna:repository
type OrderRepository interface {
	//kanna:lock update
	GetForUpdate(ctx context.Context, id model.OrderID) (model.Order, error)

	// FirstToShip passes over the orders other workers hold.
	//kanna:lock update skip-locked
	FirstToShip(ctx context.Context, s ...scopes.Order) (model.Order, error)
}
```

```go
tx, err := pool.Begin(ctx)
if err != nil {
	return err
}
defer tx.Rollback(ctx)

orders := store.NewOrderRepository(tx)
o, err := orders.GetForUpdate(ctx, id)
if err != nil {
	return err
}
if o.Status != model.OrderOpen {
	return ErrNotOpen
}
o.Status = model.OrderCanceled
if err := orders.Update(ctx, o); err != nil {
	return err
}
return tx.Commit(ctx)
```

| 強さ            | 句                  | PostgreSQL | MySQL |
|-----------------|---------------------|------------|-------|
| `update`        | `FOR UPDATE`        | 対応       | 対応  |
| `no-key-update` | `FOR NO KEY UPDATE` | 対応       | 非対応 |
| `share`         | `FOR SHARE`         | 対応       | 対応  |
| `key-share`     | `FOR KEY SHARE`     | 対応       | 非対応 |

他のトランザクションが保持している行は、解放されるまで待ちます。強さの後に `nowait` を書くと待たずにデータベースのエラーを返し、`skip-locked` を書くとその行を飛ばします。

- ロックはスコープではなくメソッドに属します。スコープはこれまでどおり行の絞り込み、並べ替え、ページングを行い、呼び出し側がロックを外したり変えたりすることはできません。
- ロックはトランザクションの間だけ続くので、ロックするメソッドはトランザクション以外の上で実行するとエラーを返します。実行の土台に `Commit` があるかどうかで判定するので、トランザクションを包む独自の `DBTX` にも `Commit` が必要です。
- `nowait`、タイムアウト、デッドロックなどでロックを取れなかった場合は、データベースのエラーをラップして返し、`orm.ErrNotFound` にはしません。リトライは呼び出し側で行います。
- `skip-locked` の `First` が返す `orm.ErrNotFound` は、条件に合う空いた行がないことを表し、行そのものがないことは意味しません。`Get`・`Find` では保持されている行をないものとして報告してしまうので、`skip-locked` を付けると生成を止めます。`nowait` を使ってください。
- スコープが読み込むリレーションは、ロックせずに読みます。
- 確実にロックされるのは存在する行だけなので、行の挿入を防げるとは当てにしないでください。
- PostgreSQL は `Offset` で飛ばした行もロックします。InnoDB は返した行ではなく走査した行をロックするので、条件に使えるインデックスがない読み取りはテーブル全体をロックします。
- `//kanna:lock` を対象のメソッドのすぐ上以外に書くと、メソッドがロックなしで生成されないように、生成を止めます。[手書きのクエリ](#手書きの-sql)や手書きのコードだけで実装するメソッドに付けた場合も同じです。ロックはそちらに書いてください。同一パッケージで生成ヘルパーを呼ぶメソッドでは、そのヘルパーにロックを引き継ぎます。
- `GetForUpdate` のようにロックしそうな名前の `Get`、`Find`、`First`、`List` に `//kanna:lock` がないと、警告が出ます。

### フック

生成 constructor は任意の repository option を受け取ります。`option.WithHook` には `hook.Hook`（Before と After の組）を渡し、repository は実行する文ごとにその前後でそれらを呼びます。どちらかは nil でかまいません。特定のロギングやトレーシングのライブラリには依存しません。クエリをログに出すには After を渡します。

```go
logQuery := func(ctx context.Context, e hook.Execution) {
    fmt.Printf("%s (%s): %v\n", e.SQL, e.Duration, e.Err)
    // ctx からリクエスト情報を取り出し、e.Args を出すかはここで決める。
}
repo := store.NewOrderRepository(db, option.WithHook(hook.Hook{After: logQuery}))
```

Before は文の開始時に `hook.Query`（`SQL string`、`Args []any`）を受け取り、文を実行する context を返します。トレーサーはここで span を開始できます。受け取った context か、そこから派生させた context を返してください。その context のキャンセルと期限は、文の実行にもそのまま効きます。After は同じ組の Before が返した context と `hook.Execution`（`Query` に `Duration time.Duration`、`Err error` を加えたもの）を受け取ります。実行と結果の読み取りが完了したとき、または Query・Scan・行の読み取りが失敗したときに呼ばれます。所要時間には結果の読み取りを含み、Before の時間は含みません。エラー変換前のエラーを渡します。生成 CRUD・`.sql` ファイルの SQL・各 Preload の SQL を、実行した文ごとに一度呼びます。条件や検証のエラーで SQL を実行しなかった場合は、どのフックも呼びません。

フックは何度でも渡せ、先に渡したものがほかを包みます。Before は渡した順に、前の Before が返した context で呼ばれ、After は逆順に、同じ組の Before が返した context で呼ばれます。そのため、Before で span を開始し、After で context の span を終える tracing のフックは、後にどんなフックがあっても自分の span を終えます。`Bind` でトランザクションへ切り替えてもフックを引き継ぎます。After がなければ時刻も取得しません。フックは並行して呼ばれるため、並行利用できるようにしてください。引数は借用した値として扱い、変更せず、呼び出しの後も保持する値はコピーしてください。PostgreSQL は pgx／`database/sql`、MySQL は `database/sql` で利用できます。生の接続を使って Go で手実装したメソッドは、生成コードの実行経路の外にあります。両 DB の example に、実行した文を出す After を渡す例があります。

### 専用の型へ読み込む projection

`Get...`・`Find...`・`First...`・`List...` は、元モデルの scope を受け取りながら別の名前付き構造体を返せます。戻り値型のフィールドから取得列を決めるため、専用型に scope は不要です。

```go
type ProductSummary struct {
    Name  string
    Price int64
}

// //kanna:repository の interface 内に宣言
ListSummaries(ctx context.Context, s ...scopes.Product) ([]ProductSummary, error)
```

`ListSummaries(ctx, scopes.Products().SKUAsc().PriceLt(2000))` は `products` から `name, price` だけを取得し、絞り込みや並べ替えには元の scope を使います。フィールド名または対応するカラム名で元モデルのフィールドに結び付け、カラム名のタグと `nullzero` の扱いを引き継ぎます。別の Go フィールド名で受け取る場合は `orm` カラムタグを指定できます。フィールドの型は元モデルと同一である必要があります。存在しないフィールド・取得列の重複・空の projection・結果型に含まれる関連は生成エラーです。読み取り専用で、絞り込み・並べ替え・ページング・ロック・不在時の契約は通常のメソッドと同じです。関連取得を指定した scope は無視せずエラーにします。集計・式は従来どおり手書き SQL と DTO で表現できます。


### JOIN する projection

scope で JOIN 先を指定すると、専用の返却型へ関連テーブルの列を取得できます。元モデルに関連フィールドを足す必要はありません。

```go
type MembershipSummary struct {
    UserID      uuid.UUID
    Role        Role
    DisplayName string // 元モデルに対応列がなければ users.display_name から推論
}

GetSummary(ctx context.Context, userID uuid.UUID, s ...scopes.Membership) (MembershipSummary, error)

summary, err := repo.GetSummary(ctx, userID, scopes.Memberships().JoinUsers())
```

一意に定まる直接の外部キーから型付きの `Join<Table>()` メソッドを生成します。`JoinUsers()` は元テーブルから `users` への外部キーを使って INNER JOIN を生成し、複合キーにも対応します。文字列の `Join("users")` も同じ外部キーを利用できます。FK がない場合は `Join("users", join.On("user_id", "id"))` のように等値条件を明示します。`github.com/go-kanna/orm/join` を import し、`join.On` には元テーブルの列、JOIN 先の列の順に渡します。複合条件は複数の `join.On` を渡します。テーブルと列は SQL 実行前にスナップショットと照合します。条件の明示により、複数の外部キーがある場合や逆向きの JOIN にも対応できます。直接の外部キーがないテーブルの取得列には `orm:"users.display_name"` のように修飾タグを指定します。自己 JOIN・別名・任意の ON 式は手書き SQL を使います。専用の読み取り projection が対象で、通常モデルの取得・関連取得 scope・書き込み・Count・Exists では JOIN を拒否します。

元モデルのフィールド対応と型の要件は維持し、JOIN 先に同名の列があっても元のテーブルの列を取得します。追加フィールドは参照先テーブルの一意なカラムから推論し、DB の型と nullable を検証します。JOIN 先の `id` のように取得元を明示する場合は、`orm:"users.id"` のようにテーブル付きの列名を指定します。必要な JOIN の不足は SQL 実行前にエラー、存在しないフィールドや参照先を特定できないフィールドは生成時エラーです。nullable な JOIN 先の列は nullable なフィールド、または文字列への明示した `nullzero` で受け取ります。

元テーブルの scope で絞り込み・並び順・カーソルを指定できます。条件は元テーブルの名前空間で評価し、並び順とページングは JOIN 後に適用します。JOIN 時の並び順には元テーブルの列を指定します。レンダラーは結果・結合・並び順に必要な列を選び、絞り込み済みの元テーブルを派生テーブルにする場合があります。別途 Preload せず、1本の SQL で取得します。両 DB の example に注文の summary へ顧客名を取得する例があります。

## 手書きの SQL

メソッドで表現できないものは `.sql` ファイルに書きます。クエリは同じ名前のリポジトリのメソッドになり、そのメソッドが実装される場所、つまり `-destination` で指定したパッケージに書きます。`-destination .` なら、インターフェースと同じディレクトリです。スコープは指定したスコープ型のメソッドになり、そのスコープ型と同じ場所に書きます。マイグレーションのように `-- query:` の行も `-- scope:` の行もない `.sql` ファイルは、kanna-orm の対象外です。

```text
repository/repository.go   //kanna:repository interfaces, MonthCounts among their methods
postgres/queries.sql       -- query: MonthCounts
scopes/order_scopes.sql    -- scope: Order.PlacedInMonth(at time.Time)
```

`-destination .` の配置は次のとおりです:

```text
repository/repository.go   //kanna:repository interfaces; //go:generate go tool kanna-orm -destination .
repository/queries.sql     -- query: MonthCounts
repository/repository_gen.go      generated private implementations and DBTX
scopes/order_scopes.sql    -- scope: Order.PlacedInMonth(at time.Time)
```

```sql
-- query: MonthCounts
SELECT date_trunc('month', placed_at) AS month, count(*) AS count
FROM orders
WHERE placed_at >= :since
GROUP BY 1
ORDER BY 1;
```

```go
MonthCounts(ctx context.Context, since time.Time) ([]MonthCount, error)

type MonthCount struct {
	Month time.Time
	Count int64
}
```

```sql
-- PlacedInMonth narrows to the orders placed in the month of at.
-- scope: Order.PlacedInMonth(at time.Time)
date_trunc('month', placed_at) = date_trunc('month', :at)
```

生成コードはそれぞれをリテラルとして保持し、パラメータはデータベースに合わせて番号付けされます:

```go
func (r OrderRepository) MonthCounts(ctx context.Context, since time.Time) ([]MonthCount, error) {
	const q = `SELECT date_trunc('month', placed_at) AS month, count(*) AS count
FROM orders
WHERE placed_at >= $1
GROUP BY 1
ORDER BY 1`
	// ...
}
```

- パラメータは、`:since` のように `:` の後に名前を続けたものです。別の `:`、英字、数字、`_`、`]` の直後の `:` はパラメータを開始しないので、`::int` のようなキャストや `arr[1:n]` のようなスライスはそのまま残ります。文字列、引用符付きの名前、コメント、ドル引用の本体の中も同様です。`describe` はこの結果の SQL をプリペアするので、読み違いがあればそこで分かります。
- クエリのパラメータの型はメソッドから決まります。構造体の引数では、公開フィールドをカラム名（タグも含む）か lower-camel のフィールド名で参照できます。SQL で使う名前に複数の引数やフィールドが一致する場合は、明示的なメソッド引数とフィールドの衝突も含め、生成を止めます。引数名・フィールド名・`orm` タグ名を調整し、参照先が一意になるようにしてください。タグを指定したフィールドも lower-camel 名で引き続き参照できます。別のパラメータ DTO を作らずモデルを渡せて、`nullzero` も適用されます。
- 結果カラムは、同じカラム名・タグのモデルフィールドへ直接読み込みます。1 カラムの結果なら scalar や enum、およびそれらの `[]T` も返せます。`T` は 1 行または `orm.ErrNotFound`、`[]T` はすべての行を返します。結果カラムのない `(int64, error)` は影響を受けた行数、1 カラムの bigint を返すクエリならその値を読み込みます。`error` だけなら結果カラムは返せません。入出力はスナップショットと照合されます。
- フィールドは名前で結果カラムを受け取るので、結果カラムにはそれぞれ固有の名前が必要です。MySQL では、カラム名が重複するクエリは情報を取得することすらできません。`SELECT o.id, c.id AS customer_id` のようにエイリアスを付けてください。
- NULL になりうる結果カラムには、nil になれるフィールドか `nullzero` を指定した文字列フィールドが必要です。データベースがカラムは NULL になりうると答えた場合、nil になれないフィールドは生成を止めます。データベースが判断できない場合は、フィールドの型をそのまま信用します。MySQL はすべてのカラムについて答えます。PostgreSQL が答えるのはテーブルから直接読み取るカラムだけで、その答えはテーブルの宣言どおりであり、外部結合によって NULL になる場合でも変わりません。`LEFT JOIN customers c` の `c.email` のようなカラムは、ポインタで保持してください。kanna-orm 自身のクエリは、結合ではなく専用のクエリでリレーションを読み込むので、これは手書きのクエリだけの問題です。
- スコープには宣言されたメソッドがないので、シグネチャを `-- scope:` の行に書きます。その行のすぐ上のコメント行は、メソッドのドキュメントになります。MySQL は文のパラメータの型を教えませんが、この方法ならその必要がありません。
- 文は、その `-- query:` や `-- scope:` の行から、次の文のコメントまたはその行までです。文の終わりにある空行とコメント行は文に含まれず、文の一番最後に付いたコメントも含まれません。そのため、スコープはコメントで終えられます。
- MySQL では、2 回使うパラメータは `?` ごとに 1 回ずつ渡します。

## ドライバと方言

スナップショットはどのデータベースから作られたかを知っているので、選ぶのはドライバだけで、`-driver` で指定します:

| データベース | `-driver` | 生成コードが使うもの |
|---|---|---|
| PostgreSQL | `pgx`（デフォルト） | `pgx.Rows`, `$1`, `= ANY($1)`, `RETURNING` |
| PostgreSQL | `database/sql`（pgx/stdlib 経由） | `*sql.Rows`, `$1`, `= ANY($1)`, `RETURNING` |
| MySQL 8.4 以上 | `database/sql`（デフォルト、go-sql-driver/mysql 経由） | `*sql.Rows`, `?`, `IN (?, ...)`, `LAST_INSERT_ID()` |

コードはそれぞれ異なり、どれもデータベースを抽象化の裏に隠しません。PostgreSQL と MySQL の違いは、コードを生成する時点で解決されます。

|  | PostgreSQL | MySQL |
|---|---|---|
| 引用符付きの名前 | `"x"` | `` `x` `` |
| パラメータ | `$1`（必要な箇所で再利用） | `?`（使うたびに 1 つ） |
| キーのリスト | `= ANY($1)` | `IN (?, ...)`（長い場合は分割） |
| 書き込みの読み戻し | `RETURNING` | `LAST_INSERT_ID()` とキーによる `SELECT` |
| Upsert | 指定したキーに対する `ON CONFLICT (...)` | 任意のユニークキーに対する `ON DUPLICATE KEY UPDATE` |
| 複数行 | `unnest`（1 つの文） | `VALUES`（長い場合は分割） |
| キーによるページング | 行の比較（順序の方向が混在する場合を除く） | 展開して書く |

値オブジェクトは `Value` メソッドと `Scan` メソッドを通してデータベースとやり取りし、他の型はドライバが変換するとおりにやり取りします。NULL になりうるカラムはポインタで保持します。database/sql 経由の場合、PostgreSQL の配列をスライスに読み込めるのは Go 1.27 以降で、そこでは pgx/stdlib が各カラムを自分でスキャンします。

## kanna の他のツールとの連携

- [kanna-value](https://github.com/go-kanna/value): 値オブジェクトは `Scan` を通して読み込まれ、`Scan` がルールをチェックします。そのため、データベースにある値をルールが拒否すると、カラムの名前を示すエラーになります。カーソルも同じようにデコードされます。
- [kanna-di](https://github.com/go-kanna/di): `NewOrderRepository` は普通のコンストラクタなので、他のものと同じようにコンテナで提供できます。
- [kanna-fixture](https://github.com/go-kanna/fixture): フィクスチャも普通のモデルなので、`Insert` でテストのデータベースに入れられます。
- [kanna-mapper](https://github.com/go-kanna/mapper): 行はモデルに直接読み込まれるので、マッピングする行の型はありません。モデルからワイヤ型（protobuf などの通信用の型）へのマッピングは、これまでどおり行ってください。

## kanna-orm がしないこと

- リレーションの書き込み。行を参照先と一緒に保存するときの順序は、トランザクションの中で自分で組み立てます。
- 変更の追跡、アイデンティティマップの保持、遅延読み込み。
- マイグレーションの作成や適用。goose などのツールを使い、その結果を `describe` してください。
- 任意の JOIN・グループ化・ネストするクエリを scope から組み立てること。読み取り projection の外部キーまたは明示した列の等値条件による INNER JOIN に対応し、それ以外は手書き SQL を使います。
- `created_at` と `updated_at` の設定、ゼロ値をカラムのデフォルト値とみなすこと。
- NULL になりうるカラムでのページング。
- pgx 経由での複数行の COPY。
- MariaDB や SQLite のサポート、1 つの生成パッケージを PostgreSQL と MySQL の両方で動かすこと。

### 親カラムを参照する単一値の取得と、親ごとの関連取得

取得先フィールドに値の取得元を宣言します。たとえば注文の現在版を承認した担当者を、承認履歴から読み込めます。

```go
type Order struct {
    ID OrderID
    Approver *string `orm:"relation=approvals"`
    Approvals []Approval
}
```

`column` を省略すると、通常の snake_case の命名規則でフィールド名から取得元のカラム名を推論します（`Approver` → `approver`）。`CurrentApprover` のように名前が異なる場合は `column=approver` を指定します。取得元のカラムが存在しなければ生成時にエラーになります。

関連先のモデルには通常の scope を宣言します。生成される `<Scope>Columns` は型付きのカラム参照で、`EqColumn`・`NeColumn`・大小比較と組み合わせられます。親の Go オブジェクトの値ではなく、SQL のカラムを表します。注文の `revision` のようにモデルに含めないカラムも、対応する DB 型が分かる場合は生成します。モデルにあるカラムはその Go 型を使います。

```go
func (s Order) WithCurrentApprover() Order {
    return s.SelectApprover(func(parent OrderColumns) relation.Single[model.Approval] {
        return Approvals().RevisionEqColumn(parent.Revision).RevokedAtIsNull().One()
    })
}

func (s Order) WithLatestApprover() Order {
    return s.SelectApprover(func(_ OrderColumns) relation.Single[model.Approval] {
        return Approvals().RevokedAtIsNull().ApprovedAtDesc().IDDesc().First()
    })
}

func (s Order) WithRecentApprovals() Order {
    return s.PreloadApprovals(func(_ OrderColumns) relation.Many[model.Approval] {
        return Approvals().ApprovedAtDesc().IDDesc().Limit(3).Many()
    })
}

orders, err := repo.List(ctx, scopes.Orders().IDAsc().Limit(20).
    WithCurrentApprover().WithRecentApprovals())
```

外部キーから基本の親子条件を生成し、コールバックで親カラムとの比較などの条件を追加します。比較するカラムの Go 型は一致する必要があります。他のコールバックから持ち出したカラム参照や、親クエリの外で使った参照はレンダリング時にエラーになります。値はバインド引数として渡し、カラム名は別にクォートします。

- `One` は一致行が最大1件であることを要求します。0件は SQL NULL、複数件は DB の cardinality エラーになります。Limit・Offset・カーソルで複数件一致を隠す指定は拒否します。
- `First` は並び順を必須とし、先頭1件を選びます。Offset で先頭を飛ばせます。Limit は自動設定するため別途指定しません。日時の後に ID を指定するなど、順序が一意になる条件を使ってください。
- `One().Required()` と `First().Required()` は一致なし・NULL を `orm.ErrRequiredRelation` として返します。NULL を保持できない格納先には Required が必要です。未選択の nullable なフィールドは nil のままです。
- `Many` は対象の親だけに絞って関連を一括取得します。Limit・Offset は親ごとに適用し、必要な場合は `ROW_NUMBER()` を使います。親別のページングには並び順が必要です。関連が0件なら空スライスを返します。関連側のカーソルは拒否するため、親はカーソル、関連は Offset でページングします。

`Select<Field>` は親と同じ SELECT に単一値のサブクエリを追加し、親の行数・ページングを維持します。複数の値を選択しても条件とプレースホルダーはそれぞれ管理します。`Preload<Field>` は別クエリによる一括読み込みで、複合外部キー・中間テーブル・読み込んだ子の関連取得にも対応します。親と関連の通常の読み取りを同じスナップショットにしたい場合は Repeatable Read のトランザクションを利用します。ロックと分離レベルは呼び出し側で明示します。1 つのフィールドは `With<Field>` か `Preload<Field>` のどちらかで読み込みます。両方を指定した scope は、読み込むときにエラーになります。

単一値の関連は読み込み専用で、INSERT・UPDATE の対象から除外します。手書き SQL に差し替える場合も、`a.approver AS approver` のようにフィールドのカラム名で返せば同じモデルへ読み込めます。PostgreSQL／MySQL の example では、現在・最新の承認者、親別の件数制限・Offset、一致なし・必須値なし・複数件一致、手書き SQL への差し替えを実行して確認します。

### 指定したカラムだけを更新する

各 scope に型付きの変更セットを生成します。`CustomerChanges()` は空の `CustomerChangeSet` を返し、setter で更新対象のカラムを指定します。setter の引数はモデルの Go 型に合わせるため、`Phone *string` には `nil` を渡して SQL NULL を設定できます。

```go
changes := scopes.CustomerChanges().
    SetName("Ann Lee").
    SetPhone(nil)
```

setter を呼ばなかったカラムは更新しません。ゼロ値も省略せず書き込み、同じカラムを再指定した場合は最後の値を使います。変更セットから派生したセットを作っても元のセットは変わりません。`nullzero` のフィールドは通常どおり空文字列を SQL NULL に変換します。主キー・DB が採番するカラム・関連フィールドには setter を生成しません。空の変更セットはエラーになります。

対象の一意キーを更新値と分けて宣言し、通常の条件スコープを追加します。

```go
UpdatePhone(ctx context.Context, id model.CustomerID,
    c scopes.CustomerChangeSet, s ...scopes.Customer) (model.Customer, error)

updated, err := repo.UpdatePhone(ctx, customerID,
    scopes.CustomerChanges().SetPhone(new("050-1234-5678")),
    scopes.Customers().PhoneIsNull())
```

PostgreSQL でモデルを返す宣言には `UPDATE ... RETURNING` を生成し、同じ文で保存後の行を取得します。条件に一致しない場合やキーが存在しない場合は `orm.ErrNotFound` を返します。複合キーや主キー以外の一意キーも利用できます。戻り値を `error` だけにすると更新結果を読み戻しません。従来のモデル全体を渡す Update にも、条件スコープとモデルの戻り値を指定できます。返すモデルにはテーブルにマップしたカラムを読み込み、関連値や preload は読み込みません。

複数行を更新する場合は、更新件数なら `(int64, error)`、更新結果の一覧なら `([]model.Customer, error)` を宣言します。WHERE 条件のない更新、並び順、ページング、関連取得のスコープは拒否します。返される行の順序は保証しません。MySQL では変更セットと `error` または更新件数を利用できます。件数は値が変わった行数で、一行更新で同じ値の行に一致した場合は成功として扱います。MySQL には UPDATE RETURNING がないため、更新したモデルを返す宣言は生成エラーとし、別 SELECT による読み戻しは行いません。

PostgreSQL／MySQL の example では、電話番号だけの更新、`SetPhone(nil)` による NULL 設定、未指定フィールドの保持、条件不一致時のエラーを実行して確認します。


### スコープで削除対象を選ぶ

スコープを受け取る `Delete` は削除件数を返します。`All` や `Batch` という接尾辞は不要で、条件・並び順・ページングで対象を指定します。

```go
Delete(ctx context.Context, s ...scopes.Order) (int64, error)

n, err := repo.Delete(ctx, scopes.Orders().
    Open().
    PlacedAtLt(before).
    PlacedAtAsc().
    IDAsc().
    Limit(batch))
```

ページングがなければ条件に一致する全行を削除します。Limit・Offset がある場合はサブクエリで対象のキーを選び、1つの文でその行を削除します。PostgreSQL／MySQL の両方で、複合主キーと NULL を許さない一意キーに対応します。どちらのキーもないテーブルでは通常の条件付き削除は利用できますが、ページングによる削除は利用できません。

Limit があっても WHERE 条件は必須です。ページングには明示した並び順が必要で、同じ値の行を安定して選ぶには `IDAsc()` のように一意キーで順序を確定させます。既存のキーセットカーソルでも対象を選べます。Limit・Offset・カーソルのない並び順や、関連取得のスコープは無視せずエラーにします。`Limit(0)` や該当行なしは `orm.ErrNotFound` ではなく削除件数 0 を返します。

従来の `Delete(ctx, id) error` は、該当行なしをエラーにする挙動を維持します。単一行の削除とスコープによる削除の区別は `All` という接尾辞ではなくメソッドの型で行います。両 DB の example では、条件に合う注文を古い順に件数を制限して削除します。

PostgreSQL ではスライスを返すと `DELETE … RETURNING` を生成し、削除した行を同じ SQL で返します。

```go
DeleteReturning(ctx context.Context, s ...scopes.Order) ([]model.Order, error)
DeleteSummaries(ctx context.Context, s ...scopes.Order) ([]DeletedOrder, error)

type DeletedOrder struct {
    ID         model.OrderID
    CustomerID model.CustomerID
}

deleted, err := repo.DeleteSummaries(ctx, scopes.Orders().
    Open().PlacedAtLt(before).PlacedAtAsc().IDAsc().Limit(batch))
```

元モデルと、読み取りの projection と同じフィールド対応・型の規則に従う専用の型を返せます。`RETURNING` には返却型のカラムだけを指定し、関連は取得しません。キー引数と scope も併用できます。条件やページングの要件は上記と同じです。該当行なしと `Limit(0)` は `orm.ErrNotFound` ではなく空の非 nil スライスを返します。並び順は削除対象の選択に使い、返却行の順序は保証しません。MySQL は `DELETE RETURNING` を持たないため、スライスを返す宣言は生成時にエラーにします。PostgreSQL の example では削除した注文を projection で返します。
