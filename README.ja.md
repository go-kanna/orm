kanna-orm は、repository のインターフェースの裏側で動くデータベースのコードを生成します。インターフェースと、それが読み取るテーブルごとのスコープ型を宣言すると、kanna-orm は実装を生成し、クエリの絞り込み、並べ替え、ページング、行が参照する先の読み込みの方法ごとに、スコープ型のメソッドも生成します。SQL はリテラルとして生成コードに残り、スキーマと合わないカラムや型で止まるのはリクエストではなく、生成かコンパイルです。

[kanna](https://go-kanna.github.io/ja/) コードジェネレータファミリーの 1 つです。Go 1.26 以上と、pgx か database/sql 経由の PostgreSQL、または database/sql 経由の MySQL 8.4 以上が必要です。

## インストール

```sh
go get -tool github.com/go-kanna/orm/cmd/kanna-orm
```

生成コードは `github.com/go-kanna/orm` のパッケージをインポートします。これは上のコマンドで依存に追加されます。これらのパッケージは標準ライブラリ以外には依存しません。ドライバは自分で用意します。手書きのコードが使うのは次のパッケージです。

| パッケージ   | 用途                                                                        |
|--------------|-----------------------------------------------------------------------------|
| `orm`        | `errors.Is` で調べるエラー `ErrNotFound`、`ErrInvalidCursor`、`ErrEmptyChangeSet` |
| `orm/scope`  | 手書きで宣言するスコープ型のフィールド `Of` と、Go で SQL を書く `Raw`        |
| `orm/option` | repository の constructor に渡す option `WithHook`、`WithClock`、`Join`     |
| `orm/hook`   | その option に渡す関数の組と、関数が受け取る値 `Hook`、`Query`、`Execution` |
| `orm/pgx`    | pgx で repository を動かす `DBTX`。DI で 1 度だけ渡す |
| `orm/stdlib` | `database/sql` で repository を動かす `DBTX`。同上 |

`orm/change` の `Set` は、生成される変更セットの `Of` が返す型で、手書きのコードが名前を書くことはありません。`orm/impl` は生成コードが動く土台で、インポートするのは生成コードだけです。

## 使い方

kanna-orm はスキーマを、マイグレーションではなくデータベースから読み取ります。データベースをマイグレーションし、`describe` でモジュールのルートにスナップショットを書き出します:

```sh
go tool kanna-orm describe -database-url "$DATABASE_URL" ./...
```

`kanna-orm.snapshot.json` はマイグレーションと一緒にコミットします。スキーマの変更がレビューで見えるようになり、生成はスナップショットだけを読むのでデータベースが要りません。

モデルのパッケージを指定すると、kanna-orm は、そのモデルのうち名前に対応するテーブルがあるものそれぞれについて、スコープ型を宣言します:

```go
package scopes

//go:generate go tool kanna-orm

//kanna:scopes model-package=../model
```

さらに、コードの他の部分が依存する repository を宣言します:

```go
package repository

//go:generate go tool kanna-orm -destination ../postgres

//kanna:repository
type Order interface {
	Get(ctx context.Context, id model.OrderID, s ...scopes.Order) (model.Order, error)
	List(ctx context.Context, s ...scopes.Order) ([]model.Order, error)
	Insert(ctx context.Context, o model.Order) (model.Order, error)
	Delete(ctx context.Context, id model.OrderID) error
}
```

モデルには、ドメインで定義したままの型を使います:

```go
package model

type OrderID uuid.UUID

type CustomerID uuid.UUID

type Order struct {
	ID         OrderID
	CustomerID CustomerID
	Status     OrderStatus
	PlacedAt   time.Time
	Memo       *string `orm:"note"`
	Lines      []OrderLine
}
```

`OrderID` と `CustomerID` は `uuid` カラムを保持します。`uuid.UUID` を元に宣言しているので、片方の値をもう片方の代わりに渡すとコンパイルエラーになります（[uuid をキーにする](#uuid-をキーにする)）。

`go generate ./...` を実行すると、スコープ型と同じディレクトリに `scopes_gen.go` が書き出されます:

```go
// Code generated by kanna-orm. DO NOT EDIT.

// Orders returns a scope over all the rows of orders.
func Orders() Order { return Order{} }

// StatusNe narrows to the rows whose status is not v.
func (s Order) StatusNe(v model.OrderStatus) Order {
	return Order{kScope(kRuntime(s.q).Where(`status <> `, v))}
}

// PlacedAtDesc orders the rows by placed_at, latest first.
func (s Order) PlacedAtDesc() Order {
	return Order{kScope(kRuntime(s.q).OrderBy(`placed_at`, true))}
}

// WithLines loads Lines, from order_lines by order_id.
func (s Order) WithLines(sub ...OrderLine) Order {
	// ...
}

// ...a method for each column and relation, and Limit, Offset, Or, Not, After, Before, Cursor, and AfterCursor.
```

`../postgres` には実装が書き出されます:

```go
// Code generated by kanna-orm. DO NOT EDIT.

// Order implements repository.Order on PostgreSQL through pgx.
type Order struct{ db kDatabase }

func newOrder(db DBTX, opts ...option.Option) Order {
	return Order{db: kDatabase{dbtx: db, options: impl.NewOptions(opts...)}}
}

// NewOrder returns Order running on db.
func NewOrder(db DBTX, opts ...option.Option) Order { return newOrder(db, opts...) }

func (r Order) Insert(ctx context.Context, o model.Order) (model.Order, error) {
	const q = `INSERT INTO orders (id, customer_id, status, placed_at, note)
VALUES ($1, $2, $3, $4, $5)
RETURNING id, customer_id, status, placed_at, note`
	var row model.Order
	err := r.db.QueryRow(ctx, q, o.ID, o.CustomerID, o.Status, o.PlacedAt, o.Memo).
		Scan(&row.ID, &row.CustomerID, &row.Status, &row.PlacedAt, &row.Memo)
	if err != nil {
		return model.Order{}, fmt.Errorf("insert into orders: %w", err)
	}
	return row, nil
}

// ...
```

呼び出し側はスコープをチェーンします:

```go
orders, err := repo.List(ctx, scopes.Orders().
	StatusNe(model.OrderCanceled).
	PlacedAtGte(lastMonth).
	WithLines().
	PlacedAtDesc().
	Limit(20))
```

スキーマと合わない宣言は、最初にそれに当たるリクエストまで持ち越さず、生成の時点で止まります:

```console
$ go generate ./...
./scopes.go:6:1: error: Order: the snapshot has no table order
  did you mean orders?
../model/order.go:12:1: error: Order.Memo: orders.note may be NULL, which a string cannot hold
  declare it as *string, or tag it orm:",nullzero" to read NULL as the empty string
./order_repository.go:12:2: error: ListByCustomer: model.Order has no field for the parameter custmerID
  did you mean customerID?
./order_repository.go:14:2: error: GetByStatus: status is not a unique key of orders, so Get cannot return one row
  use List, or add a unique index on orders (status)
```

repository のインターフェースが参照する `scopes.Order` は `//kanna:scopes` が生成するまで存在しないので、初回の実行前にはコンパイルが通りません。それでも実行は止まりません。kanna-orm はこのディレクティブから型を判断するので、`go generate` が 2 つのパッケージをどちらの順で処理しても構いません。コードが生成前のメソッドを呼び出していても構いません。その実行で生成されるメソッドがないと述べるだけのエラーでは、実行は止まりません。

kanna の生成器を 2 つ以上使うなら、必要な順に動かす [`go tool kanna gen`](https://github.com/go-kanna/kanna) で動かしてください。

## スナップショット

`describe` はデータベースに接続し、テーブルごとに、カラム（型、NULL になりうるか、identity、serial、AUTO_INCREMENT のカラムのようにデータベースが自分で値を割り当てるか）、主キー、一意キー、外部キーを記録します。さらに、引数のパッケージと、引数が指すディレクトリのうちまだパッケージがないもの（初回の生成前の repository の出力先など）にある[手書きのクエリとスコープ](#手書きの-sql)をそれぞれプリペアし、パラメータと結果カラムの型を記録します。`describe` が実行するものは、何も書き込みません。

データベースは `-database-url` で指定したもの、指定がなければ `$DATABASE_URL` です:

- `postgres://user:password@host:5432/database` は pgx 経由の PostgreSQL です。テーブルはカレントスキーマのもので、カレントスキーマは `?search_path=` で選びます。生成する SQL はテーブルをスキーマで修飾しないので、アプリの接続も同じ search_path を使ってください。
- `mysql://user:password@host:3306/database` は go-sql-driver/mysql 経由の MySQL で、`?` の後にこのドライバのオプションを指定できます。テーブルは URL で指定したデータベースのものです。

ビューとマテリアライズドビューは記録しません。これらは[手書きのクエリ](#手書きの-sql)で読んでください。`describe` はそのクエリも、ほかのクエリと同じくプリペアします。

型はデータベース自身が答えたものなので、kanna-orm にはデータベースと食い違いうる独自の SQL パーサがありません。MySQL はプリペアした文の結果の情報を返さないので、MySQL では `describe` は文を `SELECT t.* FROM (...) AS t LIMIT 0` で包んでカラムを読み取ります。この文は行を返しません。PostgreSQL では、型を SQL に書ける名前で記録します。`pg_catalog` の型は `int8` のように名前だけで、それ以外の型は `public."OrderState"` のようにスキーマと名前で、必要なところは引用して書きます。生成する SQL が、search_path に関係なくその型を指せるようにするためです。domain は基底型の名前で記録します。

スナップショットは生成に必要なものだけを記録します。そのため、`describe -check` で分かるのは、コードが現在のスキーマから生成されたことであり、2 つのスキーマが同じであることではありません:

| 記録するもの | 記録しないもの |
|---|---|
| カラムの型（宣言した長さや精度を含む）: `varchar(100)`, `numeric(10,2)` | デフォルト値の内容（デフォルト値があることだけを記録する） |
| カラムが NULL になりうるか、デフォルト値を持つか、データベースが値を割り当てるか | CHECK 制約 |
| 主キー、一意キー、外部キー | 部分インデックスの条件 |
| 手書きのクエリごとのパラメータと結果カラムの型 | トリガー、照合順序、コメント |

記録されないものだけを変更するマイグレーションでは、スナップショットは変わりません。それらをレビューしたり、2 つのデータベースを比較したりするには、マイグレーションのツールを使ってください。

スナップショットは 1 行に 1 カラムの JSON で、順序は固定です。そのため、マイグレーションは変更した行として差分に現れます:

```diff
     "orders": {
       "columns": [
         {"name": "id", "type": "uuid", "not_null": true},
         {"name": "customer_id", "type": "uuid", "not_null": true},
         {"name": "status", "type": "text", "not_null": true},
-        {"name": "placed_at", "type": "timestamptz", "not_null": true}
+        {"name": "placed_at", "type": "timestamptz", "not_null": true},
+        {"name": "note", "type": "text"}
       ],
```

モジュールのスナップショットは、ルートにある `kanna-orm.snapshot.json` の 1 つです。生成はパッケージから親ディレクトリをたどってこれを見つけます。2 つのデータベースを使うモジュールは、それぞれを別のファイルに書き出し、両方のコマンドで `-snapshot` を使ってそのファイルを指定します。

CI では、マイグレーションしたばかりのデータベースを `-check` 付きで `describe` します。スナップショットが古い場合は失敗します:

```console
$ go tool kanna-orm describe -check ./...
./kanna-orm.snapshot.json: error: out of date with the database
  orders.note (text) is in the database but not in the snapshot
  run go tool kanna-orm describe to update it
```

## スコープ型

スコープ型は、フィールドが非公開の `scope.Of[M]` だけの構造体です。`M` はテーブルの行を読み込むモデルです。これにより、スコープを絞り込めるのはそのメソッドだけになります。kanna-orm が読み書きするテーブルにはそれぞれスコープ型が 1 つあり、各モデルは 1 つのテーブルに属します。テーブルとモデルを結び付けるのはスコープ型だけです。

`//kanna:scopes model-package=../model` と書くと、モデルのパッケージの構造体のうち、スナップショットに対応する名前のテーブルがあるものそれぞれについて、`scopes_gen.go` にスコープ型を宣言します。対応するテーブルの名前は、構造体の名前をスネークケースにして最後の単語を複数形にしたもの（`OrderLine` なら `order_lines`、`Category` なら `categories`、`Person` なら `people`）です。`model-package=` には、モジュールのパッケージのインポートパスか、ファイルからの相対パスを書きます。`model-package=../model,../billing` のように、カンマで区切って複数書けます。`model-package=.` はディレクティブのあるパッケージそのものを指し、そのときのスコープ型は、モデルと分けて `OrderScope` のようにモデルの名前に `Scope` を付けた名前になります。値オブジェクトのように対応するテーブルがない構造体にはスコープ型が宣言されず、中間テーブルのように対応する構造体がないテーブルにも宣言されません。そのため、これらのパッケージの構造体は、その名前のテーブルができるとモデルになります。クエリが返す型のように、モデルでない構造体は別のパッケージに置いてください。自分のメソッドは、他の型と同じように、パッケージの別のファイルでこの型に書きます。スコープを絞るには、下の `Open` のように kanna-orm が書いたメソッドを使うか、形の決まった SQL を `.sql` ファイルに書きます。`.sql` ファイルの SQL は `describe` が確かめます（[手書きの SQL](#手書きの-sql) を参照）。実行時にプログラムが形を決める SQL は、`InMonths` のように `Raw` で書きます。こちらは実行するまで何も確かめません。`Raw` が持つのは `Where` と `OrderBy` だけで、どちらもそれまでの内容をすべて保ったスコープを返します。`Where` は、条件の SQL を `scope.SQL` の印を付けた断片で受け取り、それ以外の部分は、string も含めてすべてプレースホルダに渡す値にします。値が SQL になることはありません。SQL のない条件と、あいだに SQL のない 2 つの値は誤りで、そのスコープのどのクエリもそのエラーを返します。

```go
func (s Order) Open() Order { return s.StatusNe("closed") }

func (s Order) InMonths(months []int) Order {
	return Order{s.q.Raw().Where(scope.SQL("EXTRACT(MONTH FROM placed_at) = ANY("), months, scope.SQL(")"))}
}
```

独自の名前のスコープ型は、`//kanna:scope` で手で宣言します。`//kanna:scope` は構造体にだけ付け、ほかのものに付けると、どこからも読まれないので生成を止めます。テーブルは、`//kanna:scopes` と同じくモデルの名前から決まり、単数形など別の名前のときだけ `table=` で指定します。手で宣言したものは、同じパッケージの中では、そのモデルやテーブルについて `//kanna:scopes` が暗黙に宣言するものより優先されます。そのモデルやテーブルのスコープ型が別のパッケージにもあれば、テーブルにスコープ型は 1 つなので、生成を止めます:

```go
//kanna:scope table=person
type Person struct{ q scope.Of[model.Person] }

// People is the empty scope of person, under a name of its own.
func People() Person { return Person{} }
```

手で宣言したスコープ型には、空のスコープを返す関数を生成しません。名前もテーブルも、関数の名前が従う規約から外れているからです。ゼロ値の `Person{}` が空のスコープで、独自の名前の関数は、上の `People` のように 1 行で書けます。

リレーションがたどり着くモデルのうち、どのスコープ型にも指定されていないものがあると、生成が止まります:

```console
../model/order_line.go:9:1: error: OrderLine.Product: no scope type is declared for model.Product
  declare one where products are queried: //kanna:scope table=products
```

kanna-orm は、スコープ型ごとに次のものを生成します:

- `//kanna:scopes` が暗黙に宣言する場合は、型そのもの。
- `//kanna:scopes` が暗黙に宣言する型には、テーブルにちなんだ名前の、空のスコープを返す関数。`orders` なら `Orders()` です。単数形と複数形が同じ名前のテーブルのように、その名前が型自身の名前と同じ場合や、他で使われている場合は、型を手で宣言してください。
- カラム、リレーション、[手書きのスコープ](#手書きの-sql)ごとのメソッド。
- `Limit`、`Offset`、`Or`、`Not`、`After`、`Before`、`Cursor`、`AfterCursor`。

どのメソッドも新しいスコープを返し、レシーバは変更しません。そのため、途中まで組み立てたスコープを共有できます。`base.Limit(10)` と `base.Limit(20)` は互いの limit に影響しません。ゼロ値の `Order{}` も空のスコープです。

### カラムとフィールド

フィールドは、フィールド名をスネークケースにした名前のカラムを保持します。`CustomerID` は `customer_id` を、`PlacedAt` は `placed_at` を保持します。この変換は機械的なので、それ以外の名前のカラムを保持するフィールドは、タグでそのことを示します:

| タグ | 意味 |
|---|---|
| *（なし）* | フィールド名をスネークケースにした名前のカラム |
| `orm:"note"` | カラム `note` |
| `orm:"note,nullzero"` | nullable な文字列カラム。NULL をゼロ値へ読み込み、ゼロ値は NULL として書き込む |
| `orm:",default"` | 生成する INSERT からカラムを省略し、DB のデフォルト値を使う |
| `orm:",insertonly"` | カラムを insert でだけ書く。update と、行と突き合わせた Upsert は変えない |
| `orm:",created"` | 行を作成した時刻。kanna-orm が書く。[作成と更新の時刻](#作成と更新の時刻)を参照 |
| `orm:",updated"` | 行を最後に更新した時刻。kanna-orm が書く。[作成と更新の時刻](#作成と更新の時刻)を参照 |
| `orm:"-"` | カラムではない。kanna-orm はこのフィールドを読み書きしない |
| `orm:"fk=order_id"` | [リレーション](#リレーション)で、名前から決まらないときにたどる外部キーのカラム |
| `orm:"relation=device_topics"` | 関連する行の 1 カラムの値のスライス。[スカラーのリレーション](#スカラーのリレーション) |

カラムのないフィールド、nil になれないフィールドが保持する NULL になりうるカラム、そして insert されるテーブルで、データベースが値を必須とするのにモデルにフィールドがないカラムは、いずれも生成を止めます。それ以外の場合、モデルにフィールドがないカラムには何もしません。

nullable な文字列の欠落をフィールドのゼロ値で表す場合は `nullzero` を指定できます。`sql.Scanner` を実装した enum などの名前付き文字列型にも対応します。生成コードは `sql.Null[T]` を使うため、NULL を enum 自身の非 NULL 用 Scan へ渡さず、非 NULL の値は引き続きその Scan で検証します。テーブル操作と手書きクエリのモデルの両方に適用されます。フィールド名のスネークケースがカラム名と一致する場合、`orm:",nullzero"` とカラム名を省略できます。

[PostgreSQL](example/postgres/model/model.go) と [MySQL](example/mysql/model/model.go) の example では、省略できる注文メモに使っています。

```go
Memo string `orm:"note,nullzero"`
```

[readMemos](example/postgres/memos.go) では `MemoIsNull()` で検索し、空のメモが SQL NULL として保存され、空文字として読み込まれることと、空でないメモが保持されることを確認します。ここでは `Memo` を `note` カラムに対応させるため、カラム名を明示しています。フィールド名が `Note` なら `orm:",nullzero"` だけで十分です。

`nullzero` の代償は、NULL と `''` を区別できなくなることです。空文字は NULL として書き込まれ、読み込むときは NULL もテーブルにすでにある `''` も空文字になります。そのため、読み込んだ値で行を検索しても見つかるとは限りません。`MemoEq("")` は `= ''` で比べるので、NULL の行には一致しません。NULL の行は `MemoIsNull()` で絞り込み、NULL と `''` が別の意味を持つなら、カラムを `*string` で保持してください。

フィールドの型は、ドライバがカラムの型を読み込める型でなければなりません。`bigint` には整数型、`text` や `citext` には string、`timestamptz` や `datetime` には `time.Time`、`bytea` や `blob` には `[]byte`、`uuid` には Go 1.27 の `uuid.UUID`、それを元に宣言した型、string のいずれか、PostgreSQL の配列にはそれらのスライスです（MySQL に配列はありません）。database/sql はバイナリのカラムを string にも読み込みますが、pgx は `bytea` を string に読み込めないので、pgx では `bytea` を持つ string のフィールドで生成が止まります。MySQL のドライバは `bit(n)` のカラムをバイト列として読むので、`[]byte` で保持します。bool、整数、string で保持すると生成が止まります。真偽値には、bool で保持できる `tinyint(1)` でカラムを宣言してください。PostgreSQL の `bit(n)` と `varbit` は、pgx では `pgtype.Bits` のような `Scan` メソッドを持つ型に読み込みます。database/sql は `101` のようなテキストとして読むので、string や `[]byte` にも読み込めます。整数は `101` を百一と読んでしまうので、どちらのドライバでも、bool や整数で保持すると生成が止まります。MySQL では、`bit(n)` に書き込むパラメータは bool や数でもかまいません。`Scan` メソッドと `Value` メソッドを持つ型は自分で変換するので、どのカラムにも使えます。enum や `json` のように kanna-orm が知らないデータベースの型については、フィールドの型をそのまま信用します。ただし、そのフィールドもカラムを保持できる型でなければなりません。`json` や `jsonb` のカラムは、string、`json.RawMessage` などの `[]byte`、JSON を読み書きする `Scan` メソッドと `Value` メソッドを持つ型のいずれかで保持します。それらのメソッドを持たない struct や map は、カラムでもリレーションでもないので、生成が止まります。

カラムから読み込むフィールドは、カラムが持ちうるすべての値も保持できなければなりません。フィールドの範囲を超える値を持つ行はスキャンに失敗し、`float8` や `double` から読み込んだ `float32` は黙って精度を失います。そのため、整数フィールドの幅はカラム以上にします。`bigint` には `int64`、`integer` には `int32` です。符号付きのカラムには符号付きの型を、符号なしのカラムには符号なしの型か少し幅の広い型を使います。`bigint unsigned` には `uint64`、`int unsigned` には `int64` です。`int` と `uint` は、amd64 と同じく 64 ビット幅として扱います。書き込みには、このような幅は必要ありません。データベースは、カラムの範囲を超える値を別の値にして保存せず、拒否するからです。そのため、`integer` に対する `int` のようにカラムより幅の広いフィールドでも問題なく、パラメータの幅も問いません。`numeric` や `decimal` のカラムは、string か、`Scan` メソッドと `Value` メソッドを持つ型に読み込みます。浮動小数点数のフィールドは、正確に表せない値を丸めるので、生成が止まります。整数のフィールドが読み込めるのは、位取りが 0 で、すべての値を保持できるカラムだけです。`int64` なら `numeric(18,0)` まで、`int32` なら `numeric(9,0)` までです。精度を宣言していない `numeric` と、`sum` の結果のように手書きのクエリが返すカラムは、位取りが記録されないので、string にしか読み込めません。クエリの中でキャストしてもかまいません。`numeric` に書き込むパラメータは、どの数値型でもかまいません。

### カラムのメソッド

メソッドの名前はフィールドから決まるので、`Memo` が保持するカラム `note` からは `MemoContains` ができます。各カラムには、その型で使えるメソッドが生成されます:

| カラム | メソッド（フィールド `Status` の場合） |
|---|---|
| すべて | `StatusEq`, `StatusNe`, `StatusIn`, `StatusNotIn`, `StatusAsc`, `StatusDesc` |
| 順序のある型（数値、時刻、文字列） | 加えて `StatusLt`, `StatusLte`, `StatusGt`, `StatusGte`, `StatusBetween` |
| 文字列 | 加えて `StatusLike`、`%` と `_` をエスケープする `StatusHasPrefix` と `StatusContains`、PostgreSQL では `StatusILike` |
| NULL になりうる | 加えて `StatusIsNull`, `StatusIsNotNull` |

メソッドはフィールドの型を受け取ります。`StatusEq` は `model.OrderStatus` を受け取り、値オブジェクトは、database/sql が送るのと同じように `Value` メソッドを通してデータベースに渡ります。パターンで照合するメソッドは string を受け取ります。パターンはその型の値でなくてよいからです。`[]byte` 以外のスライスで保持されるカラム、つまり配列には、`In` も `NotIn` もありません。NULL になりうるカラムの比較メソッドは、ポインタではなく値を受け取ります。何にもマッチしない `= NULL` を書けないようにするためです。そう書いて表したかったことは `StatusIsNull` で表せます。

SQL と同じく、NULL との比較は真にも偽にもならないので、カラムが NULL の行は `IsNull` 以外の比較に一致しません。`MemoNe(v)`、`MemoNotIn(vs...)`、`MemoEq(v)` の `Not` は、どれも NULL の行を含みません。含めるなら `Or` を使います:

```go
// WHERE ... AND ((note <> $1) OR (note IS NULL))
s := scopes.Orders().Or(scopes.Orders().MemoNe(v), scopes.Orders().MemoIsNull())
```

### 独自のスコープ

名前を付けたスコープは、生成されたメソッドを使ってスコープ型に自分で書くメソッドです。生成されたメソッドと同じようにチェーンできます:

```go
// Open narrows to the orders that are not canceled.
func (s Order) Open() Order {
	return s.StatusNe(model.OrderCanceled)
}

// Recent orders by placed_at, latest first, and keeps the first n.
func (s Order) Recent(n int) Order {
	return s.PlacedAtDesc().Limit(n)
}
```

検索では、条件を 1 つずつ加えてスコープを絞り込みます:

```go
s := scopes.Orders().Open().Recent(in.PageSize)
if in.CustomerID != nil {
	s = s.CustomerIDEq(*in.CustomerID)
}
if in.Keyword != "" {
	s = s.MemoContains(in.Keyword)
}
orders, err := repo.List(ctx, s)
```

kanna-orm が生成するメソッドと同じ名前のメソッドを自分で書いている場合は、上書きせずに生成を止めます。

### Or と Not

`Or` は、渡したスコープのいずれかにマッチする行にマッチします。各スコープ自身の条件は、すべて同時に成り立つ必要があります:

```go
// WHERE ... AND ((status = $1) OR (placed_at < $2))
s := scopes.Orders().Or(
	scopes.Orders().StatusEq(model.OrderPending),
	scopes.Orders().PlacedAtLt(cutoff),
)
```

`Not` は、渡したスコープが偽になる行にマッチします。SQL と同じく、NULL を比べる条件は偽ではなく不明になるので、その行はスコープにもその `Not` にもマッチしません（[カラムのメソッド](#カラムのメソッド)を参照）。`Or` や `Not` に渡すスコープは条件だけを持ちます。並び順、limit、読み込むリレーションを持つスコープを渡すと、クエリはエラーを返します。どの選択肢も 1 つのカラムの値である場合は、`StatusIn` のほうが同じことを簡潔に表せます。

### リレーション

別のモデルのポインタ、またはモデルかそのポインタのスライスを保持するフィールドはリレーションです。たどる外部キーは名前で決まるので、他に何も書く必要はありません。スナップショットは、その外部キーがあるかの検査と、外部キーが参照するカラムを読むことにだけ使います。1 行のリレーションはポインタで、行を読み込んでいないときと、行がないときに nil です。モデルを値で持つと、そのどちらも表せないので生成を止めます:

| `Order` のフィールド | 名前で決まる外部キー | 種類 |
|---|---|---|
| `Customer *Customer` | `customers` への `orders.customer_id`。フィールド名と `_id` | belongs to |
| `Shipment *Shipment` | `orders` への `shipments.order_id`（一意キー）。モデル名と `_id` | has one |
| `Lines []OrderLine` | `orders` への `order_lines.order_id`。モデル名と `_id` | has many |
| `Tags []Tag` | モデル名とフィールド名の `order_tags` を経由し、その `order_id` と `tag_id` | many to many |

ポインタは belongs to と has one のうち、スナップショットにある方になり、スライスは has many と many to many のうち、ある方になります。両方あるときは、どちらかを選ばずに生成を止めます。ほかのカラムの外部キーはタグで指定します。そのカラムがどのテーブルのものかは関連の種類で決まり、belongs to なら自分のテーブル、has one と has many なら関連先のテーブルです。複数カラムの外部キーは、`orm:"fk=order_id,line_no"` のようにすべてのカラムを並べます。

```go
type OrderLine struct {
	OrderID OrderID
	LineNo  int
	SKU     SKU
	Product *Product `orm:"fk=sku"` // order_lines.sku to products, rather than product_id
}

type Category struct {
	ID       int64
	ParentID *int64
	Parent   *Category                       // categories.parent_id, the field's name
	Children []Category `orm:"fk=parent_id"` // categories.parent_id, rather than category_id
}
```

生成時のエラーは、何を探したかと、スナップショットのどの外部キーなら 1 つに決まるかを示します:

```console
../model/order.go:16:1: error: Order.Buyer: no foreign key of orders.buyer_id to customers reads it, nor a unique one of customers.order_id to orders
  orders.customer_id to customers reads it: tag the field orm:"fk=customer_id"
```

名前が many to many の規約に合わない中間テーブル（2 カラムのキーを参照するものなど）は、それ自身をモデルにして、has many と belongs to でたどります。どちらのテーブルの同じ名前の外部キーでも読めるポインタのように、名前で決まらないリレーションは、手書きの SQL で読み込みます。[クエリにスコープを渡す](#クエリにスコープを渡す) と [外部キー以外のカラムで関連する値を足す](#外部キー以外のカラムで関連する値を足す) を参照してください。

リレーションは、スコープが `With` メソッドで要求したときにだけ読み込まれます。`With` メソッドは関連する行のスコープを受け取り、その条件、並び順、さらに読み込むリレーションを指定できます。

```go
o, err := repo.Get(ctx, id, scopes.Orders().
	WithCustomer().
	WithLines(scopes.OrderLines().
		QuantityGt(0).
		SKUAsc().
		WithProduct()))
```

PostgreSQL では、リレーションのクエリは、行がいくつあってもリレーションごとに 1 回です。上の呼び出しは、注文、顧客、注文の明細、商品に 1 回ずつ、計 4 回のクエリを実行します。中間テーブルを経由するリレーションも、中間テーブルを JOIN して 1 回です。関連する行は、すでに読み込んだ行のキーを使い、同じキーは 1 度だけ、番号を付けて、クエリが JOIN する表として渡します。PostgreSQL では `unnest($1::int8[], $2::text[])` を使い、キーの各カラムをそのカラムの型にキャストします。MySQL では `VALUES ROW(?, ?), ...` を使い、キーを 1000 個ずつ、それぞれ別のクエリで送ります。そのため、キーはデータベースが SQL として比べます。Go の `==` の結果には左右されません。MySQL の既定の照合順序のように大文字と小文字を区別しないカラムのキーは、大文字と小文字の違う行も見つけ、`NaN` は `NaN` を見つけます。関連する行には、そのキーの番号が付いて返り、その番号で、キーを持つ行に渡されます。1 つの行に関連する行はすべて 1 つのクエリで読み込まれ、渡したスコープの順序で並びます。

- 読み込まれたスライスは決して nil になりません。関連する行がなければ空になります。nil のスライスは読み込まれていません。
- ポインタは、読み込まれていないときも関連する行がないときも nil です。この 2 つを区別するには、モデルに kanna-orm の型を持ち込むことになります。
- 関連する行に対する limit や offset は、SQL の `LATERAL` サブクエリと同じく、行ごとにページを切ります。`WithApprovals(scopes.Approvals().ApprovedAtDesc().IDDesc().Limit(3))` は、注文ごとに最新の承認を 3 件読み込みます。キーごとに、関連する行に、関連先のテーブルの主キーで終わるスコープの順序（スコープに順序がなければ主キーだけ）で `ROW_NUMBER()` の番号を振り、ページに入る行を残します。データベースがキーをどう比べても、キーごとの行は、ほかのキーの行と分けて数えます。ページは `Offset` で進めます。`After` と `Before` を渡すと、クエリはエラーを返します。主キーのないテーブルでは、スコープに順序が必要です。
- 外部キー以外のカラムで関連する値（注文の現在の版を承認した担当者など）は、自分で書くクエリで読み込みます。[外部キー以外のカラムで関連する値を足す](#外部キー以外のカラムで関連する値を足す) を参照してください。
- リレーションは読み込むだけで、決して書き込みません。`Insert` と `Update` が書き込むのはその行自身のカラムで、読み戻した行もそれらのカラムだけを保持します。
- 複数カラムの外部キーによるリレーションも、1 カラムのものと同じように読み込みます。キーの表にカラムごとの列があり、クエリはそのすべてを JOIN します。

### ページング

`Limit` と `Offset` は SQL と同じようにページングします。順序のない `Limit` や `Offset` は、SQL と同じく、データベースが読んだ順の行を残します。ページにどの行が入るかを決めるには、スコープで並べてください。行が増減してもずれないページにするには、ページの最後の行を `After` に渡します。スコープの順序でその続きから読み込みます。`After`、`Before`、`Cursor`、`AfterCursor` は主キーで続きを読むので、主キーのないテーブルや、主キーのフィールドを持たないモデルのスコープ型にはありません。その理由は、空のスコープを返す関数（手で宣言した型では `Of`）のドキュメントに書かれます:

```go
s := scopes.Orders().Open().PlacedAtDesc().Limit(20)

page, err := repo.List(ctx, s)
// WHERE status <> $1
// ORDER BY placed_at DESC, id DESC LIMIT 20
next, err := repo.List(ctx, s.After(page[len(page)-1]))
// WHERE status <> $1 AND (placed_at, id) < ($2, $3)
// ORDER BY placed_at DESC, id DESC LIMIT 20
```

- 順序のないページからは続きを読めません。順序のないスコープで行の続きを読み込むクエリはエラーを返し、`Cursor` と `AfterCursor` も同様にエラーを返します。順序は、同じ呼び出しのほかのスコープで付けてもかまいません。
- 続きを読む起点の行は 1 つです。`After` と `Before`、`After` と `AfterCursor` のように行を 2 つ渡すと、1 つのスコープでも、1 回の呼び出しの別々のスコープでも、後の行が前の行を置き換えるのではなく、クエリがエラーを返します。
- 順序が主キーで終わっていない場合は、行を並べる読み込みのすべてで、最後のカラムの向きで主キーを追加します。1 ページ目も、`After` と `Before` で続けるページも同じなので、順序の上で等しい行にも、どのページでも同じ 1 つの順序が付きます。主キーがないと、等しい行の途中で終わるページでは、その一部が黙って重複したり抜けたりします。
- 順序のすべてのカラムが同じ方向なら、条件は上の例のように行の比較になります。そうでない場合と MySQL では、`a < $1 OR (a = $1 AND b < $2)` のように展開して書かれます。
- `Before` は逆方向に進み、渡した行が先頭にあるページの 1 つ前のページに移動します。repository はそのページを末尾から読み込み、行をスコープの順序に戻して返します。
- NULL になりうるカラムで並べると、行の続きを読み込むクエリはエラーを返し、`Cursor` も同様にエラーを返します。データベースによって NULL の並ぶ位置が異なるからです。

位置をクライアントに渡すには、`Cursor` で文字列にエンコードし、`AfterCursor` でスコープにデコードします:

```go
s, err := scopes.Orders().Open().PlacedAtDesc().AfterCursor(req.PageToken)
if err != nil {
	return nil, err
}
page, err := h.orders.List(ctx, s.Limit(20))
// ...
res.NextPageToken, err = s.Cursor(page[len(page)-1])
```

カーソルは、作成時の順序と、その順序における行の値を JSON として保持します。空のカーソルは先頭を表し、別の順序で作成したカーソルはエラーになります。各値はその型を通してデコードされるので、値オブジェクトはルールをチェックします。クライアントがカーソルを改変しても、変わるのはページの開始位置だけです。kanna-orm が作ったものでないカーソル、別の順序で作成したカーソル、型が値を拒否するカーソルは、`orm.ErrInvalidCursor` を包んだエラーを返します。ハンドラは `errors.Is` で、不正なページトークンと自分の失敗を見分けられます。

## repository

`//kanna:repository` を付けたインターフェースは、データベースより上のコードがデータベースに対して何をしてよいかを宣言します。そのパッケージで `kanna-orm -destination <dir>` を実行すると、そのディレクトリの `repository_gen.go` に実装の構造体、そのコンストラクタ、実行の土台となる `DBTX`（sqlc と同じ名前）が書き出されます。インターフェース以外に付けた `//kanna:repository` と、インターフェースのメソッド以外に付けた `//kanna:conflict`・`//kanna:lock` は、どこからも読まれないので生成を止めます。

### 同じパッケージに実装する

`-destination .` を指定すると、インターフェースと生成実装を同じパッケージに置けます。インターフェースは公開する必要があります。`Category` なら、非公開の `category`、`newCategory(db DBTX, opts ...option.Option) category` コンストラクタ、値レシーバーのメソッドを生成します。関数 `NewCategory` を自分で宣言していなければ、`NewCategory(db DBTX, opts ...option.Option) Category` も生成します。自分で宣言する `NewCategory` からは `newCategory` を呼べます。スコープ型も同じパッケージに置けます（[1 つのパッケージにまとめる](#1-つのパッケージにまとめる)を参照）。

`Bind(db DBTX) Category` を宣言すると、どちらのパッケージに実装するときも、トランザクションへ切り替える `Bind` の実装を生成します。引数には、DBTX を実装した具体的な接続・トランザクションの型や、引数なしの `DBTX()` メソッドでそれを返す型も指定できます。たとえば `Bind(tx tx.Tx) Category` です。Bind は指定された接続を使う新しい実装を返し、元の実装は変更しません。引数か、その `DBTX()` が返すものは `-driver` で指定したドライバの `DBTX` を実装し、戻り値は repository 自身のインターフェースである必要があります。`Bind` を自分で書いたときは、kanna-orm は `Bind` を書きません。

repository のどのパッケージの `DBTX` も、ランタイムのものの別名です。pgx なら `github.com/go-kanna/orm/pgx` の `type DBTX = kpgx.DBTX`（kanna-orm が [Copy](#複数行の-copy) を書くパッケージでは `kpgx.CopyDBTX`）、`database/sql` なら `github.com/go-kanna/orm/stdlib` の `stdlib.DBTX` です。そのため 1 つの値ですべての repository を動かせ、DI では 1 度だけ渡せば済みます。kanna-di なら、コンテナのパッケージに provider を 1 つ書きます:

```go
import "github.com/go-kanna/orm/pgx"

func provideDBTX(reader db.Reader) pgx.DBTX { return reader }
```

別の DB で動かしたい repository には、`func provideCategory(w db.Writer) Category { return NewCategory(w) }` のように、その repository の provider を手で書きます。

アプリケーション固有のメソッドは、生成される型に直接書けます。`Bind` 以外で、認識できる動詞も手書きのクエリもないメソッドは、そこに自分で書きます。書くまでは生成が止まります。認識できる動詞か手書きのクエリがあるメソッドを自分で実装した場合は、データベースの処理を非公開のヘルパーとして生成します。手書きの `Upsert` は、行を確かめてから `r.upsert` を呼べます。ヘルパーは、その型に書いたメソッドが `r.upsert` のようにレシーバで呼んでいるときだけ生成するので、自分で SQL を実行するメソッドには生成しません。

ヘルパーのシグネチャはインターフェースのメソッドと同じで、`//kanna:conflict` と `//kanna:lock` も引き継ぎます。ヘルパーと同じ名前のメソッドがすでにあれば、生成を止めます。手書きのクエリは出力先の `.sql` ファイルに置きます。同一パッケージへの出力なら、インターフェースと同じディレクトリです。

```go
//go:generate go tool kanna-orm -destination .

//kanna:repository
type Category interface {
	Bind(db DBTX) Category
	Upsert(ctx context.Context, c model.Category) error
}

func (r category) Upsert(ctx context.Context, c model.Category) error {
	if c.Name == "" {
		return errors.New("a category needs a name")
	}
	return r.upsert(ctx, c)
}
```

### エラーの対応づけ

実装の型に `mapError` メソッドを書くと、生成するメソッドが返すエラーはすべてそれを通ります。文の実行、行の読み取り、関連の読み込みのエラーと、`orm.ErrNotFound` で、どれもメソッドが何をしていたかを付けたあとのエラーです。[PostgreSQL](example/postgres) と [MySQL](example/mysql) の example は、生成した実装の隣の [postgres/errors.go](example/postgres/postgres/errors.go) で、`Get` が読む注文が見つからないエラーを `model.ErrOrderNotFound` に変えます。repository を使う側に、データベースのエラーを見せないためです。

```go
func (Order) mapError(op orderOperation, err error) error {
    if op == orderOperationGet && errors.Is(err, orm.ErrNotFound) {
        return model.ErrOrderNotFound
    }
    return err
}
```

- 生成器は生成のときにメソッドを見つけ、メソッドがエラーを返すところに `return ..., r.mapError(orderOperationGet, err)` と書きます。nil を返すときは呼びません。
- error を 1 つ受け取るか、エラーの起きた操作と error を受け取って、error を 1 つ返す形でなければ、生成を止めます。レシーバーは実装の型で、値でもポインタでも構いません。インターフェースと同じパッケージに実装する repository では、非公開の型です（`func (*category) mapError`）。
- 操作を受け取る形（`mapError(op orderOperation, err error) error`）なら、kanna-orm は repository の名前から付けた string の型 `orderOperation` と、`Bind` を除くインターフェースのメソッドごとに、メソッド名を値に持つその型の定数（`orderOperationGet`、`orderOperationInsert`）を書きます。メソッドが読み込む関連や、書き込んだあとに読み戻す行のエラーにも、そのメソッドの操作が付きます。error だけを受け取る形なら、どちらも書かず、どのメソッドのエラーも同じように対応づけます。
- repository ごとに持てます。持たない repository は、エラーをそのまま返します。ある repository のために kanna-orm が書く名前を、手で宣言していたり、別の repository のためにも書いたりするときは、生成を止めます。
- 手で書いたメソッドは、`mapError` を自分で呼びます。操作を受け取る形なら、自分の操作を付けます（`r.mapError(orderOperationTag, err)`）。そのために生成するヘルパー（`r.upsert` など）はエラーをそのまま返すので、対応づけはメソッドで 1 回です。
- 知らないエラーは、チェーンを保つためにそのまま返してください。

操作を受け取ると、同じエラーがメソッドごとに持つ意味を分けられます。外部キーの違反は、`Insert` では顧客がないこと、`Delete` では明細がまだあることです。

```go
func (Order) mapError(op orderOperation, err error) error {
    var pg *pgconn.PgError
    if errors.As(err, &pg) && pg.Code == "23503" { // foreign_key_violation
        if op == orderOperationDelete {
            return model.ErrOrderHasLines
        }
        return model.ErrCustomerNotFound
    }
    return err
}
```

### 別のパッケージに実装する

`-destination ../postgres` のように別のパッケージを指定すると、インターフェースと同じ名前の公開構造体、`newOrder` と `NewOrder` のコンストラクタ、値レシーバーのメソッドを生成します。ほかは同じパッケージに実装するときと同じで、`Bind`、手書きしたメソッドのヘルパー、自分で宣言する `NewOrder` が使えます。インターフェースのパッケージからは生成先の `DBTX` を参照できないので、`Bind` は `Bind(tx tx.Tx) Order` のように `DBTX()` を持つトランザクションの型か、`orm/pgx` や `orm/stdlib` のランタイムの `DBTX`（kanna-orm が [Copy](#複数行の-copy) を書くパッケージでは `orm/pgx` の `CopyDBTX`）を受け取ります。

```go
// DBTX is what the repositories run on: *pgxpool.Pool, *pgx.Conn, or pgx.Tx.
type DBTX = kpgx.DBTX

func NewOrder(db DBTX, opts ...option.Option) Order
```

トランザクションは、kanna-orm がない場合と同じように開始してコミットします。コンストラクタに `pgx.Tx` か `*sql.Tx` を渡してください。

### 1 つのパッケージにまとめる

モデル、そのスコープ型、repository とその実装を、すべて 1 つのパッケージに置けます。この文書ではそれぞれを別のパッケージに置いた形で説明しますが、1 つにまとめても変わるのは次の点だけです。

```go
package store

//go:generate go tool kanna-orm -destination .

//kanna:scopes model-package=.

type Order struct {
	ID     int64
	Status string
}

//kanna:repository
type OrderRepository interface {
	List(ctx context.Context, s ...OrderScope) ([]Order, error)
	UpdateStatus(ctx context.Context, id int64, c OrderChangeSet) error
}
```

- `//kanna:scopes` が同じパッケージのモデルについて宣言するスコープ型は、モデルの名前に `Scope` を付けた名前（`OrderScope`）になります。スコープを返す関数は今までどおりテーブルの名前（`Orders()`）で、変更セットはスコープ型の名前から `Scope` を除いた名前（`OrderChangeSet` と `OrderChanges()`）です。
- 1 回の実行で `scopes_gen.go` と `repository_gen.go` の両方を書き、どちらももう一方が宣言する名前を避けます。
- 1 つの `.sql` ファイルに、パッケージの `-- scope:` と `-- query:` の両方を書けます。
- `DBTX`、`newOrderRepository`、`Orders`、`OrderChangeSet` のように、手書きのコードから見える名前をパッケージがすでに宣言していれば、生成を止めます。ただし、自分で宣言する関数 `NewOrderRepository` は生成するものを置き換えます。kanna-orm が自分のために書くヘルパーは `k` で始まり、空いている最初の名前を使います。

### メソッド

メソッドの動作は、名前の先頭の動詞で決まります。行を読み書きするメソッドでは、動詞の後ろは自由に決められます。カラムの値や集計を読むメソッドでは、`ListNames` や `SumTotal` のように、動詞の後ろでフィールドを名指します。残りはパラメータで決まります。モデル型のパラメータは書き込む行、スコープは読み込み方を表します。それ以外のパラメータは、`CustomerID` に対する `customerID` のようにモデルのフィールドの名前で、そのフィールドのカラムの値がパラメータと等しい行が対象になります。タグで決まるカラム名（`Memo` の `orm:"note"` など）はパラメータの名前になりません。この場合の名前は `memo` です。

| 動詞 | 宣言 | 動作 |
|---|---|---|
| `Get` | `Get(ctx, id model.OrderID, s ...scopes.Order) (model.Order, error)` | パラメータで指定したキーの行を読み込む。なければ `orm.ErrNotFound` を返す |
| `Find` | `Find(ctx, id model.OrderID, s ...scopes.Order) (*model.Order, error)` | パラメータで指定したキーの行を読み込む。なければ `nil, nil` を返す |
| `First` | `First(ctx, s ...scopes.Order) (model.Order, error)` | スコープにマッチする最初の行を読み込む。なければ `orm.ErrNotFound` を返す |
| `List` | `List(ctx, s ...scopes.Order) ([]model.Order, error)` | スコープにマッチするすべての行を読み込む |
| `Count` | `Count(ctx, s ...scopes.Order) (int64, error)` | スコープにマッチする行を数える |
| `Exists` | `Exists(ctx, s ...scopes.Order) (bool, error)` | マッチする行があるかどうかを返す |
| `Insert` | `Insert(ctx, o model.Order) (model.Order, error)`、または `error` のみを返す形 | 行を 1 つ、または[複数](#複数行の書き込み)書き込む |
| `Update` | `Update(ctx, o model.Order) error`、または[変更セット](#指定したカラムだけを更新する)を受け取る形 | キー以外のすべてのカラムを書き込む。そのキーの行がなければ `orm.ErrNotFound` を返す |
| `Upsert` | `Upsert(ctx, o model.Order) error`、または[変更セット](#突き合わせた行に変更セットを書く)つき | 行を insert するか、同じキー、または[別の一意キー](#upsert)を持つ行を update する |
| `Delete` | `Delete(ctx, id model.OrderID) error`、または[スコープを受け取る形](#スコープで削除対象を選ぶ) | そのキーの行、またはスコープにマッチする行を削除する |
| `Copy` | `Copy(ctx, rows []model.Order) (int64, error)` | 行を pgx の [COPY](#複数行の-copy) で書き込み、書き込んだ行数を返す |
| `Sum` | `SumTotal(ctx, s ...scopes.Order) (int64, error)` | スコープにマッチする行のカラムの合計を読む。[集計](#集計を読む)を参照 |
| `Min` | `MinPlacedAt(ctx, s ...scopes.Order) (time.Time, error)` | スコープにマッチする行のカラムの最小値を読む |
| `Max` | `MaxPlacedAt(ctx, s ...scopes.Order) (time.Time, error)` | スコープにマッチする行のカラムの最大値を読む |
| `Avg` | `AvgTotal(ctx, s ...scopes.Order) (float64, error)` | スコープにマッチする行のカラムの平均を読む |

`Get` は行の存在を必須とし、なければ `orm.ErrNotFound` を返します。`Find` はポインタを返し、不在は `nil, nil`、DB エラーは `nil, err` になります。どちらも主キーまたは一意キーを満たすキー引数が必要です。追加のスコープで条件を絞り、関連を読み込めます。ただし、`Limit`、`Offset`、`After`、`Before` で行の一部だけを残すスコープは、キーが指す行そのものを外しうるのでエラーになります。キー引数はポインタではなく値を受け取ります。nil は何にもマッチしない `= NULL` で比べることになるので、ポインタのキー引数は生成を止めます。NULL の行はスコープの `IsNull` で絞り込みます。複数行の候補から一つ選ぶ場合は `First` を使います。スコープの順序で先頭の行を、スコープに順序がなければ主キーの順で先頭の行を返します。`After` を渡すと、スコープの順序で渡した行のすぐ後の行を返します。このときは、ページと同じくスコープの順序が必要です。`Before` を渡すとエラーになります。前のページは末尾から読むので、読む行はそのページの先頭ではなく、渡した行のすぐ前の行になるからです。ポインタを返す `Find...` は、結果の構造体へのポインタでもスカラーへのポインタでも、手書き SQL で実装できます。生成された `Find` と同じく、行がなければ `nil, nil` を返します。スカラーの場合は nil が「行がない」を表すので、NULL にならない列を読みます。

```go
// customerID is customer_id: the orders of one customer.
ListByCustomer(ctx context.Context, customerID model.CustomerID, s ...scopes.Order) ([]model.Order, error)

// number is a unique key of orders, so Get reads one row by it.
GetByNumber(ctx context.Context, number model.OrderNumber) (model.Order, error)

// The key of order_lines is (order_id, sku), so Get takes both.
GetLine(ctx context.Context, orderID model.OrderID, sku model.SKU) (model.OrderLine, error)
```

- 対象のテーブルは、スコープ型がメソッドのモデルを保持するテーブルです。そのため、1 つのインターフェースで集約のすべてのテーブルを読み書きできます。
- 複数のスコープは、チェーンした場合と同じくすべてが同時に適用されます。
- `Get` は、パラメータが主キーか一意キーのカラムをすべて与えていない限り、生成を止めます。
- `Count`、`Exists`、[集計](#集計を読む)は、スコープの条件だけを使います。並び順、limit、読み込むリレーションを持つスコープを渡すと、それらを無視せずにエラーを返します。
- スコープを渡しても条件がない `Delete` は、すべての行を削除せずにエラーを返します。
- `error` だけを返す `Delete` は、`Update` と同じく、1 行も削除しなかったときに `orm.ErrNotFound` を返します。`(int64, error)` を返す `Delete` は削除した行数を返します。0 行の場合も同じです。
- メソッドと同じ名前の[手書きのクエリ](#手書きの-sql)があれば、動詞の代わりにそれが使われます。動詞も手書きのクエリもないメソッドは生成を止めます。
- 生成された構造体のメソッドを自分で書いた場合、その実装は手書きのファイルに残ります。認識できる動詞か手書きのクエリがあり、そのメソッドがレシーバでヘルパーを呼んでいれば、どちらのパッケージへの出力でも、非公開のヘルパーを生成します。

メソッドのモデルは、戻り値、書き込む行、スコープから決まります。`Delete(ctx, id)` のようにキーしか受け取らないメソッドは、repository の名前のテーブルを読み書きします。`Order` なら、`//kanna:scopes` と同じ規則でモデル `Order` のテーブルの `orders` です。`OrderRepository` も、`Repository` を外して同じ `orders` になります。repository はモデルと同じく単数形で名付けてください。`Orders` のような複数形は `orderses` になります。キーの型からは決めないので、フィールドの名前を変えたりモデルを足したりしても、メソッドが別のテーブルに移ることはありません。名前がテーブルに合わない repository は `table=` でテーブルを指定します。`table=` は名前より優先されます。どちらもなければ、そのようなメソッドで生成を止めます:

```go
//kanna:repository table=todos
type Task interface {
	Get(ctx context.Context, id uuid.UUID) (model.Todo, error) // todos, by its result
	Delete(ctx context.Context, id uuid.UUID) error            // todos, by table=
}
```

名前や `table=` のテーブルは、テーブルが決まらないメソッドのテーブルであり、それ以外には適用されません。自分のモデルが決まるメソッドはそのテーブルを読み書きするので、集約のインターフェースは引き続き集約の各テーブルを読み書きできます。

`orm.ErrNotFound` は、見つからなかったものの情報でラップされて返るので、`errors.Is` で判定するか、[`mapError`](#エラーの対応づけ) でアプリケーションのエラーに変えてください。

### uuid をキーにする

Go 1.27 以降では、`uuid` カラムは標準ライブラリの `uuid.UUID` で保持します。pgx と database/sql はこの型をそのまま読み書きします。それより前のバージョンでは、string か、`Scan` メソッドと `Value` メソッドを持つ独自の型で保持します。uuid をキーにするテーブルの宣言は、他のテーブルと同じです:

```go
type Todo struct {
	ID    uuid.UUID
	Title string
}

//kanna:repository
type TodoRepository interface {
	Get(ctx context.Context, id uuid.UUID) (model.Todo, error)
	List(ctx context.Context, s ...scopes.Todo) ([]model.Todo, error)
	Upsert(ctx context.Context, t model.Todo) error
	Delete(ctx context.Context, id uuid.UUID) error
}
```

- uuid しか受け取らないメソッドからはテーブルが決まりません。`Delete` は `TodoRepository` の名前の `todos` を、`Get` は戻り値のテーブルを読み書きします。
- uuid には比較できる順序がないので、そのカラムには `Eq`、`Ne`、`In`、`NotIn`、`Asc`、`Desc` は生成されますが、`Lt` も `Between` も生成されません。それでもページは uuid を基準に行の続きから読み込めて、カーソルは uuid をテキストとして保持します。
- デフォルトが `uuidv7()` のカラムを、自動採番の対象として自動判定はしません。`orm:",default"` がなければ、insert はゼロの UUID もそのまま書き込みます。Go 側で `uuid.NewV7()` を使って ID を与えるか、フィールドに `orm:",default"` を指定して DB のデフォルト値を使ってください。
- MySQL に `uuid` 型はなく、kanna-orm は `binary(16)` や `char(36)` に対する `uuid.UUID` も、それを元に宣言した型も受け付けません。`[]byte`、string、`Scan` メソッドと `Value` メソッドを持つ独自の型のいずれかで保持してください。

`uuid.UUID` を元に宣言した型でも uuid を保持できます。あるテーブルのキーを、別のテーブルのキーの代わりに渡すことを型で防げます:

```go
type TodoID uuid.UUID

type Todo struct {
	ID    TodoID
	Title string
}

//kanna:repository
type TodoRepository interface {
	Get(ctx context.Context, id model.TodoID) (model.Todo, error)
}
```

Go では、`uuid.UUID` を元に宣言した型と `[16]byte` を元に宣言した型を区別できないので、kanna-orm はどちらも受け付けます。database/sql がこうした型に uuid を読み込めるのは Go 1.27 からなので、スコープ型のモジュールは `go.mod` で `go 1.27` 以上を宣言する必要があります。宣言していなければ生成が止まります。`uuid.UUID` そのものは Go 1.27 以降にしかないので、この条件はかかりません。カーソルは、こうした型のキーも `uuid.UUID` と同じくテキストとして保持します。

[go-kanna/showcase](https://github.com/go-kanna/showcase) は、to-do を `uuid.UUID` をキーにして管理する to-do サービスです。

### スカラーのリレーション

関連する行の 1 カラムを、enum を含むスライスへ直接読み込めます。関連先のテーブルを指定し、中間のモデルやスコープ型は不要です。

```go
type Device struct {
    ID     uuid.UUID
    Topics []Topic `orm:"relation=device_topics"` // device_topics.topic, by device_topics.device_id
}
```

カラムは、フィールド名がその複数形になっているカラムです。[カラムの値を読む](#カラムの値を読む) と同じ規則で、`Topics` なら `topic`、`Categories` なら `category`、`TopicIDs` なら `topic_id` です。行は、has many と同じくモデル名と `_id` の外部キー（`devices` への `device_topics.device_id`）で関連づけます。ほかの名前のカラムは `column=` で、ほかのカラムの外部キーは `fk=` で指定します。`fk=` のあとに続くカラムも外部キーのカラムです（`orm:"relation=device_topics,column=name,fk=tenant_id,device_id"`）。カラムの型と NULL の許容をスライスの要素型に照合します。`leaf` と `leave` のように同じ複数形のカラムが 2 つあれば、`column=` で指定するまで生成を止めます。

`device_topics (tenant_id, device_id)` から `devices (tenant_id, id)` への関連のような複数カラムの外部キーは、組全体で検索し、親ごとに振り分けます。親モデルは参照先の両カラムを保持する必要があります。組を条件にしてバッチで読み込むため、別テナントで同じ ID があっても混在しません。キーのいずれかのポインタが nil の親は、関連の読み込み対象から外れます。

生成されたスコープには `WithTopics()` が追加されます。読み込みのスコープで指定した場合だけ、関連する値をバッチで読み込み、選択したカラムの昇順で格納します。enum の値は Scanner を通ります。読み込んだ関連が 0 件なら空のスライス、指定しなかった関連は nil です。親の INSERT と UPDATE は、この関連に触れません。モデルを読む手書きの SQL は、このフィールドのカラムを返さなくても構いません。関連の更新処理は別に実装してください。

```go
device, err := devices.GetByToken(ctx, platform, token, scopes.Devices().WithTopics())
```

### 書き込み

行は、モデルが保持するとおりに書き込まれます。値を与えなければデータベースが割り当てるカラム（serial、identity の `BY DEFAULT`、AUTO_INCREMENT）は、gorm や Rails と同じく、モデルの値がゼロなら INSERT から外してデータベースに任せ、ゼロでなければ書き込みます。採番の値に 0 は使われないので、0 を「値なし」と読めます。そのため、fixture は ID を与えられ、そのようなキーで行を突き合わせる `Upsert` も書けます（ID のない行は挿入し、ID のある行はその行を更新します）。PostgreSQL では、値を書き込んでもシーケンスは進まないので、後からデータベースが割り当てる行が同じ値を取ることがあります。シーケンスが届かない値を与えるか、後でシーケンスを進めてください。MySQL の AUTO_INCREMENT は、書き込んだ値の先へ進みます。identity の `ALWAYS` や生成カラムのように、データベースがいつも割り当てるカラムは、`default` を指定したフィールドと同じく、いつも INSERT から除外します。それ以外のゼロ値はそのまま書き込み、デフォルトが `true` のカラムに対する `false` も `false` のままです。行を作成した時刻と更新した時刻は、時計で書きます。[作成と更新の時刻](#作成と更新の時刻)を参照してください。

モデルを返す `Insert` は、データベースが保存した行を読み戻します。`error` だけを返す `Insert` は書き込むだけです。1 行は、値に応じてカラムのある文とない文の 2 つの定数のどちらかで書き込みます。複数行の Insert は、カラムを渡す行と渡さない行が混ざっていても 1 つの文で書き込みます。PostgreSQL では、値がゼロの行には、`describe` が記録した、データベースがそのカラムを割り当てる式（`nextval('orders_id_seq'::regclass)` など）の値を書きます。MySQL では `NULL` を渡し、AUTO_INCREMENT に割り当てさせます。MySQL では、データベースが主キーを割り当てた行は `LAST_INSERT_ID()` で、そうでなければ主キー（Upsert では衝突キー）で読み戻します。MySQL が数えるのは `Update` が変更した行で、見つけた行ではありません。そのため、1 行も変更されなかった場合、kanna-orm は行が存在するかを確認してから `orm.ErrNotFound` を返します。

モデルを返す `Insert`、`Update`、`Upsert` のように、書き込んだものを読み戻すメソッドは、読む前に書き込みを終えています。[`parseTime=true`](#ドライバと方言) のない MySQL で時刻を読むときのように読み戻しが失敗すると、メソッドはエラーを返しますが、行は書き込まれたままです。トランザクションの外では、再試行で行を 2 回書き込むことがあります。繰り返してはいけない書き込みはトランザクションの中で行い、エラーならロールバックしてください。MySQL で、書き込んだ行を読み戻すときにキーで見つからなければ（トリガーがキーを書き換えたときなど）、そう伝えるエラーを返します。行は書き込まれているので、`orm.ErrNotFound` ではありません。

### DB のデフォルト値

`orm:",default"` を指定したフィールドは、生成する INSERT のカラムから常に省略します。カラム名が異なる場合は `orm:"currency_code,default"` のように指定できます。スナップショットに DB の DEFAULT または自動採番の情報がないカラムに指定すると、生成を止めます。ただし、トリガーが値を入れうる[作成と更新の時刻](#作成と更新の時刻)は除きます。`default` と `nullzero` は併用できます。

```go
type Product struct {
    SKU      SKU
    Name     string
    Price    int64
    Currency string `orm:",default"`
}
```

[PostgreSQL](example/postgres) と [MySQL](example/mysql) の example では、`products.currency` に `DEFAULT 'JPY'` を定義しています。モデルに `Currency: "USD"` を渡しても INSERT では省略され、DB に保存された値が `JPY` であることを読み戻して確認します。タグがないフィールドはゼロ値も書き込みます。一括 INSERT、Upsert、[Copy](#複数行の-copy) にも適用し、手書き SQL は変更しません。

PostgreSQL では、モデルを返すメソッドが RETURNING で DB の値を読み戻します。例えば `ID uuid.UUID` に `orm:",default"` を指定すると、Go 側で採番せず `DEFAULT uuidv7()` の主キーを使えます。タグがなければ、そのキーもほかのカラムと同じく書き込まれ、ID を与えないモデルではゼロの UUID を書くので、2 行目は 1 行目と衝突します。値がゼロのときにデータベースに任せるのは、[書き込み](#書き込み)のとおり、serial、identity、AUTO_INCREMENT のカラムだけです。全カラムを省略する単一行の INSERT は DEFAULT VALUES を使います。一括書き込みには、少なくとも一つ入力カラムが必要です。

UPDATE では、タグを指定した非キーのフィールドもモデルの値を書き込みます。Upsert は競合時に、タグを指定したカラムの保存済みの値を DB のデフォルト値に戻さずに保持します。行を更新した時刻は、`default` でそれもデータベースに任せない限り、競合時にも時計で書きます。[作成と更新の時刻](#作成と更新の時刻)を参照してください。

MySQL では、RETURNING がないので、モデルを返すメソッドは、AUTO_INCREMENT、書き込んだ主キー、または Upsert の衝突キーで行を読み戻します。その読み戻しに要るキーを `default` が省くと、モデルを返すメソッドは生成を止めます。`error` だけを返すメソッドは読み戻さないので、省いても構いません。MySQL の一括書き込みはモデルを返しません。

### 作成と更新の時刻

`CreatedAt` という名前のフィールドは行を作成した時刻を、`UpdatedAt` という名前のフィールドは行を最後に更新した時刻を保持します。kanna-orm はどちらも時計で書くので、repository より上のコードはどちらも設定しません。別の名前にするモデルは、フィールドに `created` と `updated` のタグを付けます。どちらかのタグを付けたフィールドのあるモデルでは、その種類の名前は特別ではありません:

```go
type Customer struct {
	ID        CustomerID
	Name      string
	CreatedAt time.Time // created_at
	UpdatedAt time.Time // updated_at
}

type Event struct {
	ID         int64
	Kind       string
	InsertedAt time.Time `orm:",created"`
	ModifiedAt time.Time `orm:",updated"`
}
```

| 書き込み | 作成の時刻 | 更新の時刻 |
|---|---|---|
| 1 行か複数行の `Insert`、行を insert する `Upsert` | 時計の時刻 | 時計の時刻 |
| 行か変更セットの `Update`（キーでもスコープでも） | そのまま | 時計の時刻 |
| 行と突き合わせた、行か変更セットの `Upsert` | そのまま | 時計の時刻。ただし空の変更セットは行をそのままにする |
| [`Copy`](#複数行の-copy) | 行の値 | 行の値 |

- どちらも `time.Time` です。ほかの型（ポインタを含む）は生成を止めます。1 つのモデルに同じ種類のフィールドが 2 つあっても止めます。
- モデルが保持する値によらず、時計の時刻で上書きします。ゼロを埋めるべき値とはみなさず、値があっても残しません。メソッドは時計を 1 回だけ読むので、1 回の書き込みの行はどれも同じ時刻になります。
- 変更セットには、どちらの setter（`SetUpdatedAt` など）もありません。変更セットの `Update` は、設定したカラムと一緒に更新の時刻を書きます。空の変更セットの `Update` は、それでもエラーです。
- `Copy` は、元の時刻を保ったままの取り込みのように、行をそのまま流し込むので、行が保持する時刻を書き、時計を読みません。新しい行には時刻を与えるか、複数行の `Insert` で書いてください。
- どちらかに `insertonly` を付けると生成を止めます。作成の時刻はもともと insert でだけ書き、更新の時刻は行を書くたびに書くからです。タグを外してください。
- どちらかに `default` を付けると、データベースが DEFAULT かトリガーで値を入れるとみなします。kanna-orm は、insert、update、Upsert、Copy のどの文でもそのカラムを書かず、行を返すメソッドは読み戻します（PostgreSQL では RETURNING で）。スナップショットはトリガーを記録しないので、ほかの `default` と違い、スナップショットにデフォルトの記録は要りません。DEFAULT もトリガーもない NOT NULL のカラムは、行を insert するときに失敗します。
- [手書きの SQL](#手書きの-sql) は、これらのカラムも書いたとおりに書きます。

時計は、コンストラクタに `option.WithClock` で `orm.Clocker` を渡さない限り `time.Now` です。フックを `option.WithHook` で渡すのと同じで、`Bind` も引き継ぎます。`Now` は書き込むメソッドの context を受け取るので、時計を context で運ぶアプリは、メソッド 1 つでつなげます:

```go
type clock struct{ now time.Time }

func (c clock) Now(context.Context) time.Time { return c.now }

repo := postgres.NewCustomer(db, option.WithClock(clock{now: time.Date(2026, 1, 15, 9, 0, 0, 0, time.UTC)}))
```

実装の型に自分で書いたメソッドは、`r.db` で文を実行するとフックを通るのと同じく、`r.db.Now(ctx)` で同じ時計の時刻を得ます。これらのカラムを書く自分の SQL も、テストが与えた時刻になります:

```go
func (r Customer) Touch(ctx context.Context, id model.CustomerID) error {
	_, err := r.db.Exec(ctx, "UPDATE customers SET updated_at = $1 WHERE id = $2", r.db.Now(ctx), id)
	return err
}
```

kanna-orm は、時計がどのゾーンで時刻を返しても、UTC にしてから書きます。`r.db.Now(ctx)` も UTC の時刻を返します。`timestamptz` のカラムは、どちらでも同じ瞬間を保存します。PostgreSQL の `timestamp` のカラムはゾーンを保存せず、pgx は時刻を見た目の数字のまま書くので、Rails が `created_at` を保存するのと同じく UTC の時刻が入り、UTC として読めます。MySQL の `datetime` もゾーンを保存しません。go-sql-driver/mysql は、`loc` が指すゾーン（DSN で指定しなければ UTC）で書いて読むので、同じテーブルを使うプログラムは同じ `loc` を指定してください。読み戻した時刻のロケーションは、ドライバが読むロケーションです。pgx は `timestamptz` をローカルのゾーンで、`timestamp` を UTC で読み、go-sql-driver/mysql は `loc` で読みます。表示するゾーンには `In` で変えられます。

データベースは、時刻を Go より粗く保存することがあります。PostgreSQL はマイクロ秒まで、MySQL はカラムの小数秒の桁まで（`datetime(6)` は 6 桁、`datetime` は 0 桁）保存します。メソッドが返すモデルは、PostgreSQL では RETURNING で、MySQL では読み戻しで、保存された時刻を保持するので、時計が与えた時刻と違うことがあります。カラムが保存する精度で比べるか、テストの時計にはその精度で割り切れる時刻を与えてください。

両 DB の example は、顧客が登録し変更した時刻を、自分で設定する時計で書きます。

### Upsert

`Upsert` は、主キーで既存の行と突き合わせます。別の一意キーで突き合わせるには、`//kanna:conflict` でそのカラムを指定します:

```go
// package model
type User struct {
	ID        int64
	TenantID  int64
	Email     string
	Name      string
	CreatedAt time.Time
}

// package repository

//kanna:repository
type User interface {
	// UpsertByEmail meets the user of a tenant by their email address.
	//kanna:conflict tenant_id,email
	UpsertByEmail(ctx context.Context, u model.User) (model.User, error)
}
```

```sql
-- PostgreSQL
INSERT INTO users (tenant_id, email, name, created_at)
VALUES ($1, $2, $3, $4)
ON CONFLICT (tenant_id, email) DO UPDATE SET name = EXCLUDED.name
RETURNING id, tenant_id, email, name, created_at

-- MySQL, which then reads back by LAST_INSERT_ID() the row inserted or updated
INSERT INTO users (tenant_id, email, name, created_at)
VALUES (?, ?, ?, ?) AS new
ON DUPLICATE KEY UPDATE id = LAST_INSERT_ID(users.id), name = new.name
```

カラムはテーブルの主キーか一意キーと完全に一致しなければならず、データベースがいつも値を割り当てるカラムは含められません。insert はそのカラムの値を渡さないので、行を突き合わせる材料にならないからです。突き合わせた行では、そのキーのカラム、主キー、`insertonly` を指定したカラム、[作成の時刻](#作成と更新の時刻)を除くすべてのカラムを更新します。更新するカラムが残らない場合は、キーに自分自身を設定するので、行はやはり読み戻されます。

キーには NULL になりうるカラムも含められますが、SQL は 2 つの NULL を等しいとみなさないので、そこが NULL の行はどの行とも突き合いません。そのような行の Upsert は毎回行を挿入し、NULL として書き込む `nullzero` のフィールドのゼロ値でも同じです。PostgreSQL では、`NULLS NOT DISTINCT` で宣言した一意キーなら行と突き合います。それ以外では、行と突き合わせるキーのカラムを NOT NULL にしてください。

MySQL は、Upsert が行を突き合わせるキーに限らず、どの一意キーの競合でも行を更新します。そのため、ほかにも一意キーを持つテーブルの Upsert には、キーを指定していても、主キーで突き合わせていても、警告が出ます。insert が主キーを書くとき（`ID` が 0 でない行の AUTO_INCREMENT の `id` など）は、主キーもほかの一意キーに数えます。突き合わせるキーのカラムをすべて含むキーは、別の行と競合しないので数えません。生成カラム（`GENERATED ALWAYS AS`）を含むキーは数えます。その値は insert が書くカラムから計算されるからです。PostgreSQL では、ほかのキーで競合すると一意制約の違反のエラーになり、何も書きません。

```console
./user_repository.go:14:2: warning: UpsertByEmail: on MySQL, a conflict on (id) or (tenant_id, login) also updates the row
  users has unique keys other than (tenant_id, email)
  an insert writes id of a row whose ID is not zero
```

`orm:",insertonly"` を指定したフィールドは、利用者がどこから登録したかのように、insert でだけ書きます。`Update` と、行と突き合わせた Upsert はそのカラムを変えず、変更セットにもその setter はありません。insert から省く `default` と一緒に指定すると、どこでも書かれなくなるので、生成を止めます。

#### 突き合わせた行に変更セットを書く

[変更セット](#指定したカラムだけを更新する)を受け取る Upsert は、キーが一致する行がなければ行を insert し、突き合わせた行には変更セットだけを書きます:

```go
//kanna:conflict email
UpsertByEmail(ctx context.Context, c model.Customer, changes scopes.CustomerChangeSet) (model.Customer, error)
```

```go
changes := scopes.CustomerChanges().SetName(c.Name)
if c.Phone != nil {
	changes = changes.SetPhone(c.Phone)
}
stored, err := repo.UpsertByEmail(ctx, c, changes)
```

example の `Customer` repository は、この形で顧客を登録します。登録済みの顧客は名前を書き換え、電話番号は渡されたときだけ書き換えます。行の値は insert にだけ使うので、変更セットは NULL や空文字も、ほかの値と同じように書きます。空の変更セットは、キーが一致する行がなければ行を insert し、あれば突き合わせた行をそのまま読み戻します。衝突キーのカラムを書く変更セットはエラーを返し、何も書きません。キーの変更は `Update` で行ってください。変更セットを受け取れるのは 1 行の Upsert だけです。複数行の Upsert が受け取ると、突き合わせたすべての行に同じ値を書くことになるので、生成を止めます。

文は変更セットの中身によらず同じです。書けるカラムは、変更セットが値を渡せばその値に、渡さなければ保存済みの値のままになります。[更新の時刻](#作成と更新の時刻)は、変更セットが何か値を渡せば時計の時刻になるので、空の変更セットではそのままです。

```sql
-- PostgreSQL
ON CONFLICT (email) DO UPDATE SET name = CASE WHEN $5 THEN $6 ELSE customers.name END, phone = CASE WHEN $7 THEN $8 ELSE customers.phone END

-- MySQL
ON DUPLICATE KEY UPDATE id = LAST_INSERT_ID(customers.id), name = IF(?, ?, customers.name), phone = IF(?, ?, customers.phone)
```

[`Add`](#指定したカラムだけを更新する) のあるカラムには、変更セットが値を足すとき、その値を保存済みの値に足す 2 つ目の分岐があります。顧客に `Visits int32` のフィールドがあれば、`AddVisits(1)` は突き合わせた顧客の来店を 1 回数え、突き合わせる行がなく insert する行には、その行自身の値が入ります:

```sql
-- PostgreSQL
visits = CASE WHEN $9 THEN $10 WHEN $11 THEN customers.visits + $12 ELSE customers.visits END

-- MySQL
visits = IF(?, ?, IF(?, customers.visits + ?, customers.visits))
```

`visits = visits + 1` のように保存済みの値に数を足すのは `Add` で書けます。突き合わせた行から計算するそのほかの値は、[手書きの SQL](#手書きの-sql) で書きます。

### 複数行の書き込み

スライスを渡した `Insert` や `Upsert` は、その中のすべての行を書き込みます:

```go
InsertLines(ctx context.Context, lines []model.OrderLine) error
```

```sql
-- PostgreSQL: one statement for any number of rows
INSERT INTO order_lines (order_id, sku, quantity)
SELECT * FROM unnest($1::uuid[], $2::text[], $3::int[])
```

- PostgreSQL では、戻り値が `([]model.OrderLine, error)` なら `RETURNING` で行を読み戻します。複数行の `Update` や `Delete` と同じく、行の順は保証しません。どの行がどれかを知るには、自分で持っているキーで突き合わせるか、行を 1 つずつ Insert してください。
- MySQL では、行を `VALUES (?, ?, ?), (?, ?, ?), ...` で送り、1 つの文に入るプレースホルダの数を超える場合は複数の文に分割します。すべて成功するかすべて失敗するかにしたい場合は、コンストラクタにトランザクションを渡してください。
- MySQL には `RETURNING` がないので、MySQL では `error` だけを返す形以外は生成を止めます。
- PostgreSQL は、2 つの行が同じキーを持つ upsert を拒否します。
- `unnest` は配列の配列を平坦にするので、PostgreSQL では配列カラムを持つテーブルは生成を止めます。行を 1 つずつ書き込むか、[COPY](#複数行の-copy) してください。

### 複数行の COPY

`Copy` は、スライスの行を PostgreSQL の COPY で、pgx の `CopyFrom` を通して書き込み、書き込んだ行数を返します:

```go
CopyEvents(ctx context.Context, events []model.Event) (int64, error)
```

```sql
-- what the hooks see
COPY "events" ("kind", "tags", "note") FROM STDIN
```

COPY には `RETURNING` も `ON CONFLICT` もなく、行単位のセキュリティ（RLS）のあるテーブルには使えないので、複数行の `Insert` の中身を切り替えずに、別の動詞にしています。

- 書き込むカラムは、複数行の `Insert` と同じです。`default` を指定したカラムと、データベースがいつも割り当てるカラムは外します。[作成と更新の時刻](#作成と更新の時刻)は行が保持するとおりに書き、時計を読みません。1 つの COPY はカラムをすべての行に書くか、どの行にも書かないので、値を与えなければデータベースが割り当てるカラム（serial など）は、すべての行が値を与えれば書き込み、どの行も与えなければデータベースに任せ、両方の行が混ざればエラーを返して何も書きません。その場合は行を分けて COPY してください。
- `unnest` では書けない配列も、ほかの値と同じように書き込みます。
- 行がなければ何も実行せず、0 を返します。
- エラーは、そのメソッドの操作とともに [`mapError`](#エラーの対応づけ) を通ります。フックには、`Args` のない COPY の文として見えます。
- pgx は値をバイナリ形式で書くので、PostgreSQL の enum 型のように pgx が知らない型のカラムは、`Conn.LoadType` と `pgtype.Map.RegisterType` で先に接続へ型を登録する必要があります。
- pgx が必要です。MySQL や `-driver database/sql` では、生成を止めます。そこでは複数行の `Insert` で書き込んでください。

kanna-orm が `Copy` か、手で書いた `Copy` が呼ぶヘルパーを書くパッケージは、`DBTX` を `kpgx.CopyDBTX` として宣言します。`CopyFrom` を持つランタイムの `DBTX` で、`*pgxpool.Pool`、`*pgx.Conn`、`pgx.Tx` はどれも持っているので、COPY できない接続はコンパイルで止まります。注文を複製する `CopyOrder` のように、自分で書いてヘルパーを呼ばない `Copy...` のメソッドは `DBTX` を変えません。`r.db.CopyFrom` を自分で呼ぶには、kanna-orm が書く `Copy` を宣言してください。そのようなパッケージの各 repository の `Bind` は、`Bind(db kpgx.CopyDBTX) Order` のようにそれを受け取るか、`DBTX()` がそれを返すトランザクションを受け取ります。COPY できないものを受け取る `Bind` では、生成を止めます。DI では、`DBTX` に加えて `CopyDBTX` も渡します:

```go
func provideCopyDBTX(pool *pgxpool.Pool) pgx.CopyDBTX { return pool }
```

[PostgreSQL](example/postgres) の example は、この形で注文の承認を COPY し、After がその COPY を出力します。

### 指定したカラムだけを更新する

各スコープに型付きの変更セットを生成します。名前はスコープ型の名前から末尾の `Scope` を除いたもので、`OrderScope` の変更セットも `OrderChangeSet` です。同じパッケージの 2 つのスコープ型の変更セットが同じ名前になるときは、生成を止めます。`CustomerChanges()` は空の `CustomerChangeSet` を返し、setter で更新対象のカラムを指定します。setter の引数はモデルの Go 型に合わせるため、`Phone *string` には `nil` を渡して SQL NULL を設定できます。

```go
changes := scopes.CustomerChanges().
    SetName("Ann Lee").
    SetPhone(nil)
```

Go でもデータベースでも数で、NULL にならないカラムには、`Set` のほかに `Add` があります。フィールドが整数か浮動小数点数の型（それを基にした型を含む）で、カラムが整数、decimal、浮動小数点数の型のものです。`Add` は保存済みの値に文の中で足すので、読んでから書くまでの間に行われた更新を失いません:

```go
changes := scopes.OrderLineChanges().AddQuantity(1)
```

```sql
-- PostgreSQL
UPDATE "order_lines" SET "quantity" = "quantity" + $1 WHERE ...

-- MySQL
UPDATE `order_lines` SET `quantity` = `quantity` + ? WHERE ...
```

NULL を許すカラムには `Add` はありません。NULL に数を足しても NULL のままだからです。`Valuer` で文字列として保存する数にもありません。

setter を呼ばなかったカラムは更新しません。ゼロ値も省略せず書き込みます。同じカラムに `Set` か `Add` をもう一度呼ぶと、後に呼んだほうを使います。変更セットから派生したセットを作っても元のセットは変わりません。`nullzero` のフィールドは通常どおり空文字列を SQL NULL に変換します。主キー・DB が採番するカラム・`insertonly` を指定したカラム・[作成と更新の時刻](#作成と更新の時刻)・関連フィールドには setter を生成しません。変更セットの `Update` は、更新の時刻を時計で書きます。空の変更セットの `Update` は `orm.ErrEmptyChangeSet` を返します。ハンドラは `errors.Is` でこれを調べて、何も変えないリクエストを拒否できます。[Upsert](#突き合わせた行に変更セットを書く) ではエラーになりません。

対象の一意キーを更新値と分けて宣言し、通常の条件スコープを追加します。

```go
UpdatePhone(ctx context.Context, id model.CustomerID,
    c scopes.CustomerChangeSet, s ...scopes.Customer) (model.Customer, error)

updated, err := repo.UpdatePhone(ctx, customerID,
    scopes.CustomerChanges().SetPhone(new("050-1234-5678")),
    scopes.Customers().PhoneIsNull())
```

変更セットの Update は、書き換える行をキーかスコープ（または両方）で選びます。どちらも受け取らない宣言は、全行を書き換えるのではなく、生成を止めます。PostgreSQL でモデルを返す宣言には `UPDATE ... RETURNING` を生成し、同じ文で保存後の行を取得します。条件に一致しない場合やキーが存在しない場合は `orm.ErrNotFound` を返します。複合キーや主キー以外の一意キーも利用できます。戻り値を `error` だけにすると更新結果を読み戻しません。モデル全体を渡す Update にも、条件スコープとモデルの戻り値を指定できます。返すモデルにはテーブルにマップしたカラムを読み込み、関連値は読み込みません。

複数行を更新する場合は、更新件数なら `(int64, error)`、更新結果の一覧なら `([]model.Customer, error)` を宣言します。返される行の順序は保証しません。MySQL では変更セットと `error` または更新件数を利用できます。件数は値が変わった行数で、一行更新で同じ値の行に一致した場合は成功として扱います。MySQL には UPDATE RETURNING がないため、更新したモデルを返す宣言では生成を止め、別の SELECT で読み戻すことはしません。

両 DB の example は、この方法で顧客の電話番号を更新し、`SetPhone(nil)` で消します。

一意キーを引数に取らずスコープを受け取る変更セットの Update は、[スコープを受け取る `Delete`](#スコープで削除対象を選ぶ) と同じように行を選びます。どの行かは、条件・並び順・ページングで言います。`UpdateByCustomer(ctx, customerID, c, s...)` の `customerID` のように、一意キーでない列の引数は、`Delete` の引数と同じく条件です。

```go
Update(ctx context.Context, c scopes.OrderChangeSet, s ...scopes.Order) (int64, error)

n, err := repo.Update(ctx, scopes.OrderChanges().SetMemo("Follow up"), scopes.Orders().
    Open().
    PlacedAtAsc().
    IDAsc().
    Limit(batch))
```

ページングがなければ条件に一致する全行を更新します。Limit・Offset がある場合は、ページつきの `Delete` と同じくサブクエリで対象のキーを選び、1 つの文でその行を更新します。PostgreSQL と MySQL の両方で使えます。規則も `Delete` と同じです。Limit があっても WHERE 条件は必須です。ページは同じスコープの読み込みと同じように選びます。並び順は最後にキーを足し、並び順のないページはデータベースが先に読んだ行になります。`After` や `Before` で続けるページでも対象を選べます。Limit・Offset・カーソルのない並び順や、関連取得のスコープは無視せずエラーにします。主キーも NULL を許さない一意キーもないテーブルでは、ページングによる更新は利用できません。`Limit(0)` や該当行なしは `orm.ErrNotFound` ではなく、件数 0 か空のスライスを返します。並び順は更新対象の選択に使い、返却行の順序は保証しません。両 DB の example では、open の注文のうち古い 2 件に、件数を制限してメモを書きます。

一意キーやモデル全体を受け取る Update は、キーが示す 1 行を書き換えるので、スコープは条件だけを取ります。並び順・ページング・関連取得は、`Get` のページングと同じくエラーです。

一意キーを引数に取らずスコープを受け取る変更セットの Update に `//kanna:lock` を付けると、ページングの有無によらずそのサブクエリで行を選び、そこでロックします。まとめて更新するワーカーどうしが、他が保持している行を飛ばせます。[行ロック](#行ロック)を参照してください。


### スコープで削除対象を選ぶ

スコープを受け取る `Delete` は、削除した行数を返します。どの行かは、条件・並び順・ページングで言います。

```go
Delete(ctx context.Context, s ...scopes.Order) (int64, error)

n, err := repo.Delete(ctx, scopes.Orders().
    Open().
    PlacedAtLt(before).
    PlacedAtAsc().
    IDAsc().
    Limit(batch))
```

ページングがなければ条件に一致する全行を削除します。Limit・Offset がある場合はサブクエリで対象のキーを選び、1つの文でその行を削除します。PostgreSQL／MySQL の両方で、複合主キーと NULL を許さない一意キーに対応します。どちらのキーもないテーブルでは通常の条件付き削除は利用できますが、ページングによる削除は利用できません。

Limit があっても WHERE 条件は必須です。削除するページは、同じスコープの読み込みと同じように選びます。並び順は最後にキーを足すので、並び順で同じ値の行も読み込みと同じ行が選ばれます。並び順のないページは、SQL と同じく、データベースが先に読んだ行になります。`After` や `Before` で続けるページでも対象を選べます。Limit・Offset・カーソルのない並び順や、関連取得のスコープは無視せずエラーにします。`Limit(0)` や該当行なしは `orm.ErrNotFound` ではなく削除件数 0 を返します。

キーで削除する `Delete(ctx, id) error` は、そのキーの行がなければ `orm.ErrNotFound` を返します。2 つを区別するのは、名前ではなくメソッドの形です。両 DB の example では、条件に合う注文を古い順に件数を制限して削除します。

PostgreSQL ではスライスを返すと `DELETE … RETURNING` を生成し、削除した行を同じ SQL で返します。

```go
DeleteReturning(ctx context.Context, s ...scopes.Order) ([]model.Order, error)
DeleteSummaries(ctx context.Context, s ...scopes.Order) ([]DeletedOrder, error)

type DeletedOrder struct {
    ID         model.OrderID
    CustomerID model.CustomerID
}

deleted, err := repo.DeleteSummaries(ctx, scopes.Orders().
    Open().PlacedAtLt(before).PlacedAtAsc().IDAsc().Limit(batch))
```

元モデルと、読み取りの projection と同じフィールド対応・型の規則に従う専用の型を返せます。`RETURNING` には返却型のカラムだけを指定し、関連は取得しません。キー引数とスコープも併用できます。条件やページングの要件は上記と同じです。該当行なしと `Limit(0)` は `orm.ErrNotFound` ではなく空の非 nil スライスを返します。並び順は削除対象の選択に使い、返却行の順序は保証しません。MySQL は `DELETE RETURNING` を持たないため、スライスを返す宣言は生成時にエラーにします。

### 行ロック

`//kanna:lock` を付けた `Get`、`Find`、`First`、`List` は、読んだ行をトランザクションが終わるまでロックします。読んだ内容が、書き戻す時点でも変わっていないようにするためです:

```go
//kanna:repository
type Order interface {
	//kanna:lock update
	GetForUpdate(ctx context.Context, id model.OrderID) (model.Order, error)

	// FirstToShip passes over the orders other workers hold.
	//kanna:lock update skip-locked
	FirstToShip(ctx context.Context, s ...scopes.Order) (model.Order, error)
}
```

```go
tx, err := pool.Begin(ctx)
if err != nil {
	return err
}
defer tx.Rollback(ctx)

orders := postgres.NewOrder(tx)
o, err := orders.GetForUpdate(ctx, id)
if err != nil {
	return err
}
if o.Status != model.OrderOpen {
	return ErrNotOpen
}
o.Status = model.OrderCanceled
if err := orders.Update(ctx, o); err != nil {
	return err
}
return tx.Commit(ctx)
```

| 強さ            | 句                  | PostgreSQL | MySQL |
|-----------------|---------------------|------------|-------|
| `update`        | `FOR UPDATE`        | 対応       | 対応  |
| `no-key-update` | `FOR NO KEY UPDATE` | 対応       | 非対応 |
| `share`         | `FOR SHARE`         | 対応       | 対応  |
| `key-share`     | `FOR KEY SHARE`     | 対応       | 非対応 |

他のトランザクションが保持している行は、解放されるまで待ちます。強さの後に `nowait` を書くと待たずにデータベースのエラーを返し、`skip-locked` を書くとその行を飛ばします。

一意キーを引数に取らずスコープを受け取る [変更セットの `Update`](#指定したカラムだけを更新する)、つまりページングできる Update にも `//kanna:lock` を付けられます。そのときは、スコープがページングするかどうかによらずサブクエリでキーを選び、ロックはそのサブクエリに付けます。待つ行、エラーになる行、飛ばす行は、書き換えるはずの行です:

```go
// UpdateFree writes the orders no other worker holds.
//kanna:lock update skip-locked
UpdateFree(ctx context.Context, c scopes.OrderChangeSet, s ...scopes.Order) (int64, error)

n, err := orders.UpdateFree(ctx, scopes.OrderChanges().SetStatus(model.OrderShipped),
    scopes.Orders().Open().PlacedAtAsc().IDAsc().Limit(batch))
```

このロックにトランザクションは要りません。トランザクションの外では文の間、中ではトランザクションが終わるまで続きます。どの UPDATE のロックとも同じです。一意キーを受け取る Update や、行を選ぶ主キーも NULL を許さない一意キーもないテーブルでは、生成を止めます。MySQL でも止めます。InnoDB は文が走査した行をロックするので、MySQL の UPDATE は、サブクエリが飛ばした行を読んで待つことがあるからです。

- ロックはスコープではなくメソッドに属します。スコープはこれまでどおり行の絞り込み、並べ替え、ページングを行い、呼び出し側がロックを外したり変えたりすることはできません。
- 読み込みのロックはトランザクションの間だけ続くので、ロックする読み込みはトランザクションの外で実行するとエラーを返します。実行の土台に `Commit` があるか、`Commit` のあるものを包んでいるかで判定します。トランザクションを包む独自の `DBTX` は、中身を返す `Unwrap` で包んでいることを示します。`orm/pgx` なら `Unwrap() pgx.DBTX`、`database/sql` なら `Unwrap() stdlib.DBTX` です。包みが何重でもたどります。
- `nowait`、タイムアウト、デッドロックなどでロックを取れなかった場合は、データベースのエラーをラップして返し、`orm.ErrNotFound` にはしません。リトライは呼び出し側で行います。
- `skip-locked` の `First` が返す `orm.ErrNotFound` は、条件に合う空いた行がないことを表し、行そのものがないことは意味しません。`Get`・`Find` では保持されている行をないものとして報告してしまうので、`skip-locked` を付けると生成を止めます。`nowait` を使ってください。
- スコープが読み込むリレーションは、ロックせずに読みます。
- 確実にロックされるのは存在する行だけなので、行の挿入を防げるとは当てにしないでください。
- PostgreSQL は `Offset` で飛ばした行もロックします。InnoDB は返した行ではなく走査した行をロックするので、条件に使えるインデックスがない読み取りはテーブル全体をロックします。
- `//kanna:lock` を対象のメソッドから空行で離して書くか、`//kanna:repository` を付けていないインターフェースのメソッドに書くと、警告を出します。その行はどこからも読まれず、メソッドはロックなしで生成されます。インターフェースのメソッド以外に書いた場合は、生成を止めます。[手書きのクエリ](#手書きの-sql)や手書きのコードだけで実装するメソッドに付けた場合は、生成を止めます。ロックはそちらに書いてください。スコープを受け取るクエリでは、[何をロックするか](#クエリにスコープを渡す)に気をつけてください。生成ヘルパーを呼ぶメソッドでは、そのヘルパーにロックを引き継ぎます。
- `GetForUpdate` や `ListForShare` のように名前がロックで終わる `Get`、`Find`、`First`、`List` は、`//kanna:lock` がないと警告が出て、別の強さの `//kanna:lock` なら生成を止めます。`GetForUpdateForm` のように後ろに語が続く名前は、ロックのことを言っていないものとして扱います。

### フック

生成 constructor は任意の repository option を受け取ります。`option.WithHook` には `hook.Hook`（Before と After の組）を渡し、repository は実行する文ごとにその前後でそれらを呼びます。どちらかは nil でかまいません。特定のロギングやトレーシングのライブラリには依存しません。クエリをログに出すには After を渡します。

```go
logQuery := func(ctx context.Context, e hook.Execution) {
    fmt.Printf("%s (%s): %v\n", e.SQL, e.Duration, e.Err)
    // Use ctx for request metadata; choose whether to log e.Args.
}
repo := postgres.NewOrder(db, option.WithHook(hook.Hook{After: logQuery}))
```

Before は文の開始時に `hook.Query`（`SQL string`、`Args []any`）を受け取り、文を実行する context を返します。トレーサーはここで span を開始できます。受け取った context か、そこから派生させた context を返してください。その context のキャンセルと期限は、文の実行にもそのまま効きます。After は同じ組の Before が返した context と `hook.Execution`（`Query` に `Duration time.Duration`、`Err error` を加えたもの）を受け取ります。実行と結果の読み取りが完了したとき、または Query・Scan・行の読み取りが失敗したときに呼ばれます。所要時間には結果の読み取りを含み、Before の時間は含みません。`mapError` を通す前のエラーを渡します。生成 CRUD・`.sql` ファイルの SQL・関連を読み込む SQL を、実行した文ごとに一度呼びます。[Copy](#複数行の-copy) は、`COPY "events" ("kind", "tags", "note") FROM STDIN` のような COPY の文として、`Args` なしで見えます。条件や検証のエラーで SQL を実行しなかった場合は、どのフックも呼びません。

フックは何度でも渡せ、先に渡したものがほかを包みます。Before は渡した順に、前の Before が返した context で呼ばれ、After は逆順に、同じ組の Before が返した context で呼ばれます。そのため、Before で span を開始し、After で context の span を終える tracing のフックは、後にどんなフックがあっても自分の span を終えます。`option.Join` は、複数の option を渡した順のまま 1 つにします。型ごとに値を 1 つ持つ DI に渡すときに使います。`Bind` でトランザクションへ切り替えてもフックを引き継ぎます。After がなければ時刻も取得しません。フックは並行して呼ばれるため、並行利用できるようにしてください。引数は借用した値として扱い、変更せず、呼び出しの後も保持する値はコピーしてください。PostgreSQL は pgx／`database/sql`、MySQL は `database/sql` で利用できます。実装の型に自分で書いたメソッドも、実装のただ 1 つのフィールド `r.db` で文を実行すればフックを通ります。メソッドは DBTX と同じで、pgx では `r.db.Exec`、`r.db.Query`、`r.db.QueryRow`（kanna-orm が Copy を書くパッケージでは `r.db.CopyFrom` も）、`database/sql` では `r.db.ExecContext`、`r.db.QueryContext`、`r.db.QueryRowContext` です。`*sql.Rows` と `*sql.Row` は、行の読み込みを包んでフックに通すことができない型なので、`database/sql` のクエリは、`r.db.QueryContext` か `r.db.QueryRowContext` が返った時点で、行を読む前に終わったとフックに見えます。`Duration` と `Err` に行の読み込みは入りません。kanna-orm が生成するメソッドは、どちらのドライバでも行をフックを通して読みます。両 DB の example に、実行した文を出す After を渡す例があります。

### カラムの値を読む

行ではなくカラムの値を返す `Get`・`First`・`Find`・`List` は、そのカラムを読みます。読むのは、名前の動詞の後ろが表すフィールドのカラムで、`GetName` なら `Name` です。`List` ではテーブル名と同じ規則で作る複数形で、`ListNames` なら `Name`、`ListCategories` なら `Category` です。頭字語で終わるフィールドは s を付け、`ListCustomerIDs` なら `CustomerID` です。戻り値は projection と同じく、フィールドの型の値、`Find` ならそのポインタ、`List` ならそのスライスです。名前が言うのは何を読むかだけです。どの行かはいつもどおりキーとスコープで言うので、`ListNamesByPrice` のような名前は生成を止めます。条件・並び順・件数制限・オフセット・カーソル・`//kanna:lock` は行を読むときと同じように使えます。関連を読み込むスコープは、読み込む先の行がないのでエラーです。重複値は保持し、該当行がなければ空のスライスを返します。

```go
ListNames(ctx context.Context, s ...scopes.Product) ([]string, error)
```

```go
names, err := products.ListNames(ctx, scopes.Products().PriceLt(2000).PriceAsc())
```

両 DB の example は、この方法で手ごろな価格の商品名を読みます。

名前はロックで終わってもよく、終わりのロックを外した残りでフィールドを決めます。`//kanna:lock key-share` の `ListIDsForKeyShare` は、`ID` を読み、その行を `FOR KEY SHARE` でロックします。

```go
//kanna:lock key-share
ListIDsForKeyShare(ctx context.Context, s ...scopes.Order) ([]model.OrderID, error)
```

### 専用の型へ読み込む projection

`Get...`・`Find...`・`First...`・`List...` は、元モデルのスコープを受け取りながら別の名前付き構造体を返せます。戻り値型のフィールドから取得列を決めるため、専用型にスコープは不要です。

```go
type ProductSummary struct {
    Name  string
    Price int64
}

// Inside a //kanna:repository interface:
ListSummaries(ctx context.Context, s ...scopes.Product) ([]ProductSummary, error)
```

`ListSummaries(ctx, scopes.Products().SKUAsc().PriceLt(2000))` は `products` から `name, price` だけを取得し、絞り込みや並べ替えには元のスコープを使います。フィールドは、同じ名前の元モデルのフィールドに結び付け、そのカラム名のタグと `nullzero` の扱いを引き継ぎます。別の名前のフィールドは、`orm:"note"` のようにカラム名のタグで指定します。フィールドの型は元モデルと同一である必要があります。存在しないフィールド、取得列の重複、空の projection、結果型に含まれる関連があると、生成を止めます。読み取り専用です。絞り込み・並べ替え・ページング・ロックはモデルを読むときと同じく使え、行がないときも、モデルを読むときと同じく `Get` と `First` は `orm.ErrNotFound` を、`Find` は nil を返します。関連取得を指定したスコープは無視せずエラーにします。projection には行のグループの[集計](#集計を読む)を持たせられます。そのほかの式は手書き SQL と DTO で表現できます。


### JOIN する projection

projection は、元のテーブルが参照するテーブルの列を、入れ子の struct で読めます。struct なら INNER JOIN、struct のポインタなら LEFT JOIN で、結合する行がなければ nil です:

```go
type MembershipSummary struct {
    UserID  uuid.UUID
    Role    Role
    User    struct{ DisplayName string }  // users, by user_id: INNER JOIN
    Inviter *struct{ DisplayName string } // users, by inviter_id: LEFT JOIN
}

GetSummary(ctx context.Context, userID uuid.UUID, s ...scopes.Membership) (MembershipSummary, error)
```

```sql
SELECT memberships.user_id, memberships.role, "user".display_name, inviter.id IS NOT NULL, inviter.display_name
FROM "memberships"
INNER JOIN users AS "user" ON "user".id = memberships.user_id
LEFT JOIN users AS inviter ON inviter.id = memberships.inviter_id
```

- 結合するテーブルは、[リレーション](#リレーション)と同じく、フィールド名と `_id` の外部キーが参照するテーブルです。ほかのカラムの外部キーは `orm:"fk=created_by"` のようにタグで指定し、複数カラムなら `orm:"fk=tenant_id,customer_id"` と並べます。
- 入れ子の struct のフィールドは、projection のフィールドが元モデルに結び付くのと同じく、結合するテーブルのモデルのフィールドに、名前かカラム名のタグで結び付きます。結合するテーブルには、そのモデルを示すスコープ型が要ります。そのスコープの条件や関連は持ち込みません。
- テーブルの別名はフィールド名のスネークケースです。そのため、同じテーブルを 2 回結合することも、`parent_id` で categories の `Parent *struct{ Name string }` を読むような自己結合もできます。元のテーブルや別のフィールドと別名が重なれば、生成を止めます。
- LEFT JOIN は、外部キーが参照するカラムで結合する行があるかを見分けます。結合した行のカラムが NULL でも、nil か `nullzero` のゼロ値として読み、struct はそのまま残ります。
- 入れ子の型は専用の struct で、モデルにはしません。モデルは[リレーション](#リレーション)で読みます。入れ子の struct の中の struct、元のテーブルの外部キーが参照しないテーブル、Delete での結合は、手書きの SQL で書きます。
- スコープの条件は元のテーブルだけを読み、並び順と LIMIT は結合のあとに付きます。そのため、INNER JOIN で落ちた行は数えず、`First` は結合結果の先頭を読みます。並び順は元のテーブルの列で指定します。テーブルを結合する projection には `//kanna:lock` を付けられません。モデルを読んで行をロックするか、`FOR UPDATE OF` のように対象のテーブルを指定してロックするクエリを手で書いてください。

### 集計を読む

`Sum`・`Min`・`Max`・`Avg` は、名前の動詞の後ろが表すフィールドのカラムの、合計・最小値・最大値・平均を読みます。`SumTotal` なら `Total` の合計です。[カラムの値を読む](#カラムの値を読む)ときと同じく、名前が言うのは何を読むかだけです。どの行かはいつもどおりキーとスコープで言うので、`SumTotalByStatus` のような名前は生成を止めます。

```go
SumTotal(ctx context.Context, s ...scopes.Order) (int64, error)
MaxPlacedAt(ctx context.Context, s ...scopes.Order) (*time.Time, error)
AvgTotal(ctx context.Context, customerID model.CustomerID) (float64, error)
```

```sql
SELECT coalesce(sum(total)::bigint, 0) FROM orders WHERE ...
```

- `Sum` と `Avg` は数のカラムを読みます。数のカラムとは、整数か浮動小数の型、またはそれを基にした型のフィールドが保持するカラムです。`Min` と `Max` は数・文字列・時刻のカラムを読みます。それ以外のカラムは生成を止めます。MySQL は `ENUM` のカラムの値を、型が宣言した順ではなく文字列として比べます。
- `Sum`・`Min`・`Max` は、フィールドの型の値か、そのポインタを返します。NULL になりうるカラムの `*int64` のフィールドなら、`int64` か `*int64` です。`Avg` は `float64` か `float32`、またはそのポインタを返します。整数の平均が整数になることはまれだからです。ほかの型は生成を止めます。型に収まらない合計は、値を切り詰めずに、実行時のエラーになります。
- マッチする行がないとき、またはマッチした行のカラムがすべて NULL のとき、値を返す形は、`Sum` なら 0 を、`Min`・`Max`・`Avg` なら `Get` と同じく `orm.ErrNotFound` を返します。ポインタを返す形は、`Find` と同じく nil を返します。
- スコープは `Count` と同じく条件だけを使います。並べ替える、ページングする、リレーションを読み込むスコープを渡すと、エラーを返します。
- PostgreSQL では、`bigint` の合計は `numeric` になるので、整数の合計を `bigint` に、平均を `double precision` にキャストします。MySQL では、整数の平均は小数 4 桁の `DECIMAL` になるので、平均を `DOUBLE` にキャストします。整数の合計は `DECIMAL` のままで、database/sql がフィールドの型に読みます。収まらなければエラーです。

`List` で読む projection は、行のグループの集計を持てます。`Count` という名前の `int64` のフィールドはグループの行数を、`Sum`・`Min`・`Max`・`Avg` にモデルのフィールドの名前を続けた名前のフィールドはそのカラムの集計を、その動詞が返す型で保持します。行は残りのフィールドでグループ化します。残りのフィールドは、ほかの projection と同じく、モデルのカラムを指します:

```go
type StatusCount struct {
	Status model.OrderStatus
	Count  int64
}

ListStatusCounts(ctx context.Context, s ...scopes.Order) ([]StatusCount, error)
```

```sql
SELECT status, count(*) FROM orders WHERE ... GROUP BY status
```

- グループには必ず行がありますが、NULL になりうるカラムは、グループのすべての行で NULL のことがあります。そのカラムの `Min`・`Max`・`Avg` はポインタにします。そのようなグループでは nil です。`Sum` は 0、ポインタなら nil です。
- グループの順序は、SQL と同じく決まっていません。スコープは `Count` と同じく条件だけを使います。
- 集計の projection は `List` で読み、1 つ以上のフィールドでグループ化し、テーブルを結合せず、`//kanna:lock` を付けません。そうでなければ生成を止めます。集計のフィールドにはタグを付けません。集計のフィールドと同じ名前（`Count` など）のフィールドがモデルにもあれば、どちらを読むとも取れるので、生成を止めます。
- HAVING、集計の値での並び替え、そのほかの形は、DTO を返す[手書きの SQL](#手書きの-sql) で書きます。

## 手書きの SQL

メソッドで表現できないものは `.sql` ファイルに書きます。クエリは同じ名前の repository のメソッドになり、そのメソッドが実装される場所、つまり `-destination` で指定したパッケージに書きます。動詞で始まる名前のメソッドは、その動詞の生成メソッドと同じものを返します。どこで読んでも動詞が同じことを言うためです。`Get` と `First` は 1 行で、なければ `orm.ErrNotFound`、`Find` はポインタで、なければ nil、`List` はスライス、`Count` は結果の 1 列の `int64`、`Exists` は結果の 1 列の `bool`、`Sum`・`Min`・`Max` は結果の 1 列の値かそのポインタ、`Avg` は結果の 1 列の `float64` か `float32`、またはそのポインタ、`Insert`・`Update`・`Upsert`・`Delete` は error だけか、影響した行数の `(int64, error)` か、`RETURNING` が返す行です。それ以外は生成を止めます。`MonthCounts` のように動詞で始まらない名前なら、何を返しても構いません。`-destination .` なら、インターフェースと同じディレクトリです。スコープは指定したスコープ型のメソッドになり、そのスコープ型と同じ場所に書きます。マイグレーションのように `-- query:` の行も `-- scope:` の行もない `.sql` ファイルは、kanna-orm の対象外です。

```text
repository/repository.go   //kanna:repository interfaces, MonthCounts among their methods
postgres/queries.sql       -- query: MonthCounts
scopes/order_scopes.sql    -- scope: Order.PlacedInMonth(at time.Time)
```

`-destination .` の配置は次のとおりです:

```text
repository/repository.go   //kanna:repository interfaces; //go:generate go tool kanna-orm -destination .
repository/queries.sql     -- query: MonthCounts
repository/repository_gen.go      generated private implementations and DBTX
scopes/order_scopes.sql    -- scope: Order.PlacedInMonth(at time.Time)
```

```sql
-- query: MonthCounts
SELECT date_trunc('month', placed_at) AS month, count(*) AS count
FROM orders
WHERE placed_at >= :since
GROUP BY 1
ORDER BY 1;
```

```go
MonthCounts(ctx context.Context, since time.Time) ([]MonthCount, error)

type MonthCount struct {
	Month time.Time
	Count int64
}
```

```sql
-- PlacedInMonth narrows to the orders placed in the month of at.
-- scope: Order.PlacedInMonth(at time.Time)
date_trunc('month', placed_at) = date_trunc('month', :at::timestamptz)
```

生成コードはそれぞれをリテラルとして保持し、パラメータはデータベースに合わせて番号付けされます:

```go
func (r Order) MonthCounts(ctx context.Context, since time.Time) ([]MonthCount, error) {
	const q = `SELECT date_trunc('month', placed_at) AS month, count(*) AS count
FROM orders
WHERE placed_at >= $1
GROUP BY 1
ORDER BY 1`
	// ...
}
```

- パラメータは、`:since` のように `:` の後に名前を続けたものです。別の `:`、英字、数字、`_`、`]` の直後の `:` はパラメータを開始しないので、`::int` のようなキャストや `arr[1:n]` のようなスライスはそのまま残ります。文字列、引用符付きの名前、コメント、ドル引用の本体の中も同様です。`describe` はこの結果の SQL をプリペアするので、読み違いがあればそこで分かります。
- クエリのパラメータの型はメソッドから決まります。構造体の引数では、公開フィールドを、カラムにかかわらず lower camel case のフィールド名（`CustomerID` なら `:customerID`）で参照します。SQL で使う名前に一致する引数やフィールドは 1 つでなければならず、フィールドと同じ名前の引数があれば生成を止めます。別のパラメータ DTO を作らずモデルを渡せて、`nullzero` も適用されます。
- 結果カラムは、同じカラム名・タグのモデルフィールドへ直接読み込みます。1 カラムの結果なら scalar や enum、およびそれらの `[]T` も返せます。`T` は 1 行または `orm.ErrNotFound`、`[]T` はすべての行を返します。結果カラムのない `(int64, error)` は影響を受けた行数、1 カラムの bigint を返すクエリならその値を読み込みます。`error` だけなら結果カラムは返せません。入出力はスナップショットと照合されます。
- フィールドは名前で結果カラムを受け取るので、結果カラムにはそれぞれ固有の名前が必要です。MySQL では、カラム名が重複するクエリは情報を取得することすらできません。`SELECT o.id, c.id AS customer_id` のようにエイリアスを付けてください。
- NULL になりうる結果カラムには、nil になれるフィールドか `nullzero` を指定した文字列フィールドが必要です。データベースがカラムは NULL になりうると答えた場合、nil になれないフィールドは生成を止めます。データベースが判断できない場合は、フィールドの型をそのまま信用します。MySQL はすべてのカラムについて答えます。PostgreSQL が答えるのはテーブルから直接読み取るカラムだけで、その答えはテーブルの宣言どおりであり、外部結合によって NULL になる場合でも変わりません。`LEFT JOIN customers c` の `c.email` のようなカラムは、ポインタで保持してください。kanna-orm 自身のクエリは、結合ではなく専用のクエリでリレーションを読み込むので、これは手書きのクエリだけの問題です。
- スコープには宣言されたメソッドがないので、シグネチャを `-- scope:` の行に書きます。その行のすぐ上のコメント行は、メソッドのドキュメントになります。MySQL は文のパラメータの型を教えませんが、この方法ならその必要がありません。別のパッケージの型は、スコープ型のパッケージの Go ファイルが import している名前で書きます。そこで import していない名前は、そのスコープ型のテーブルのモデルを宣言したファイルの import で解決し、`model.Status` のようにモデル自身のパッケージの名前でも解決します。そのため、`//kanna:scopes` が宣言するスコープ型のパッケージは、モデルやモデルが使う型のために import を書く必要がありません。Go と同じくパッケージ自身の import が先なので、モデルのファイルやパッケージとは別のパッケージを同じ名前で使いたいときは、パッケージの Go ファイルで import します。どれにも当たらないパッケージは、`import _ "time"` のように、スコープ型のパッケージの Go ファイルでこのためだけに import します。
- スコープは、上のものなら `SELECT 1 FROM orders WHERE date_trunc('month', placed_at) = date_trunc('month', :at::timestamptz);` のように、そのテーブルに対する文としても書けます。条件だけでは SQL の linter が解析できないので、クエリと同じように linter にかけられるようにするためです。kanna-orm は条件だけを取り出して自分の文に入れるので、文の形はこれ 1 つに限ります。`1` を選び、テーブルに別名は付けません。条件を入れる先では、別名は意味を持たないからです。条件の後には `;` しか置けません。テーブルの名前は、データベースと同じように読みます。引用符で囲んだ名前は書いたとおりに比べます。囲まない名前は、PostgreSQL では小文字にして比べ（PostgreSQL がそう読むため）、MySQL では大文字と小文字を区別せずに比べます（MySQL の規則はサーバーの設定で変わるため）。`SELECT` で始まるそれ以外の文は生成を止めます。`id IN (SELECT ...)` のような条件は、これまでどおり条件です。
- 文は、その `-- query:` や `-- scope:` の行から、次の文のコメントまたはその行までです。文の終わりにある空行とコメント行は文に含まれず、文の一番最後に付いたコメントも含まれません。そのため、スコープはコメントで終えられます。
- MySQL では、2 回使うパラメータは `?` ごとに 1 回ずつ渡します。
- `[]byte` と `Value` メソッドを持つ型を除くスライスの引数は、値の並びです。nil のスライスは、空のスライスと同じく値のない並びです。PostgreSQL では `= ANY(:ids)` のように配列として受け取り、nil は `NULL` ではなく空の配列として渡します。MySQL では、メソッドの実行時に値ごとの `?` に展開します。値がないとき、`IN` の括弧のすぐ内側なら、行のないサブクエリ（空の集合）にします。`IN (:ids)` はどの行にも一致せず、`NOT IN (:ids)` はすべての行に一致します。PostgreSQL の `= ANY` と `<> ALL` と同じです。`FIELD(id, :ids)` のようにそれ以外の場所では `NULL` にします。

### クエリにスコープを渡す

`ListWithCustomers(ctx, s ...scopes.Order)` のように、メソッドがスコープを受け取るクエリは、1 つのテーブルとして読みます。クエリの結果をスコープのテーブルの行として読み、スコープがそれを絞り込み、並べ、ページを切り、関連を読み込みます。kanna-orm は、クエリをメソッド名の `WITH` に入れ、その後にスコープを書きます:

```sql
-- query: ListWithCustomers
SELECT o.id, o.customer_id, o.status, o.placed_at, o.note, c.name AS customer_name
FROM orders o
JOIN customers c ON c.id = o.customer_id;
```

```go
// OrderWithCustomer is an order with the name of its customer, which the query adds to it.
type OrderWithCustomer struct {
	model.Order
	CustomerName string
}

ListWithCustomers(ctx context.Context, s ...scopes.Order) ([]OrderWithCustomer, error)
```

```sql
WITH list_with_customers AS (SELECT o.id, ..., c.name AS customer_name FROM orders o JOIN customers c ON ...)
SELECT orders.id, ..., orders.customer_name FROM list_with_customers AS orders WHERE (status = $1) ORDER BY id
```

- `Get`・`Find`・`First`・`List` のどれかで、スコープのモデルの行か、モデルを値で埋め込んだ構造体の行を読みます。埋め込んだ構造体のほかのフィールドは、クエリが足すカラムを保持します。結果のカラムとフィールド（モデルのフィールドも含む）は 1 対 1 で対応し、クエリが足すカラムはモデルのカラムと重なってはいけません。スコープを受け取らないクエリは、これまでどおり何を返しても構いません。
- クエリのパラメータが先、スコープのパラメータが後です。
- クエリの中の `LIMIT` は、スコープが絞り込む前に行を残します。クエリの中の `ORDER BY` はスコープが読む行を並べないので、`LIMIT` のない `ORDER BY` には警告が出ます。行はスコープで並べてください。
- クエリの中のロック（`FOR UPDATE SKIP LOCKED` など）は、スコープが絞り込み、ページを切る前に、クエリが読む行をロックします。`Limit(1)` でもクエリのすべての行をロックし、それを飛ばす 2 つ目のワーカーは 1 行も得ません。そのため、ロックには警告が出ます。ページの行をロックするには、ページの条件と `LIMIT` をクエリに書き、スコープを受け取らないようにしてください。こうしたメソッドに `//kanna:lock` を付けると、ほかの手書きのクエリと同じく生成を止めます。
- `After`、`Before`、`Cursor` はモデルの主キーでページを続けるので、結果の行は主キーで区別できなければなりません。2 回現れる行には、それぞれに関連を読み込みます。
- 速さはデータベースが決め、kanna-orm は約束しません。PostgreSQL 12 以降は 1 回だけ使う `WITH` を文に取り込み、MySQL は取り込むことも、先に全体を読むこともあります。遅いときは、絞り込む条件をクエリの中に書いてください。

### 外部キー以外のカラムで関連する値を足す

注文の現在の版を承認した担当者のように、外部キー以外のカラムで行に関連する値は、自分で書くクエリで読み込みます。行はいつもどおりスコープ、カーソル、リレーションで読み、そのキーの値をもう 1 本のクエリで読んで、Go でつなぎます:

```sql
-- query: ListApprovers
SELECT o.id AS order_id, a.approver
FROM orders AS o
LEFT JOIN approvals AS a ON a.order_id = o.id AND a.revision = o.revision AND a.revoked_at IS NULL
WHERE o.id = ANY(:ids) -- IN (:ids) on MySQL
ORDER BY o.id;
```

```go
orders, err := repo.List(ctx, scopes.Orders().Open().PlacedAtDesc().Limit(20).WithLines())
// ...
ids := make([]model.OrderID, len(orders))
for i, o := range orders {
	ids[i] = o.ID
}
approvers, err := repo.ListApprovers(ctx, ids)
```

## 渡すスコープの検査

スコープによっては、repository のメソッドが、SQL を送る前に毎回失敗します。`Count` は条件だけを取るので、行を並べ替えるスコープを渡すと `orm: Count takes conditions alone, but its scope orders the rows` を返します。`kanna-orm vet` は、そうした呼び出しを、実行せずに見つけます。

```sh
go tool kanna-orm vet ./...
```

```text
usecase/orders.go:42:21: error: Count takes conditions alone, but its scope orders the rows
  scopes/scopes.go:22:11: Latest orders them by PlacedAtDesc
```

呼び出したメソッドの位置に、その呼び出しが返すエラーと同じ文で報告します。失敗の原因が別の場所（自分で書いたスコープの中など）にあるときは、その場所も添えます。見つけるのは次のものです。

- 条件だけを取るもの（`Count`、`Exists`、`Sum`、`Min`、`Max`、`Avg`、集計の projection の `List`、一意キーかモデル全体を取る `Update`、`Or` と `Not` の選択肢）に渡したスコープの順序、ページング、関連の読み込み。`Get` と `Find` に渡したページング。projection、1 列の読み込み、`Delete`、変更セットを取る `Update` に渡した関連の読み込み
- 条件のないスコープでの `Delete` と、変更セットを取る `Update`（すべての行に効いてしまう）。`Limit` も `Offset` もない、順序つきの `Delete` と、一意キーを取らない変更セットの `Update`。主キーも NULL のない一意キーもない表の、ページつきの `Delete` と、一意キーを取らない変更セットの `Update`
- 関連を読むスコープの `After` と `Before`。1 行の関連を読むスコープの `Limit` と `Offset`
- `Limit` と `Offset` に渡した負の定数。何も代入しない変更セットを渡した `Update`。メソッドが書けない列（upsert が行を突き合わせる列など）に代入する変更セット

vet は、関数の中の変数、スコープを組み立てる分岐、スコープを読むクロージャ、自分で書いたスコープのメソッドと関数をたどります。interface を通した呼び出しは、kanna-orm がそれに生成した実装が実行するとおりに検査します。報告するのは、どの経路でも失敗する呼び出しだけです。2 ページ目以降でだけページングするスコープのように、一部の経路でだけ失敗するものは報告しません。vet がたどらないスコープ（引数、フィールド、パッケージ変数、スライスで来たもの）も報告しません。テストのファイルは検査しません。テストでは、わざと失敗させることがあるためです。vet が通っても、vet が失敗を見つけた呼び出しがないというだけで、失敗する呼び出しがないことの証明ではありません。

## ドライバと方言

スナップショットはどのデータベースから作られたかを知っているので、選ぶのはドライバだけで、`-driver` で指定します:

| データベース | `-driver` | 生成コードが使うもの |
|---|---|---|
| PostgreSQL | `pgx`（デフォルト） | `pgx.Rows`, `$1`, `= ANY($1)`, `RETURNING` |
| PostgreSQL | `database/sql`（pgx/stdlib 経由） | `*sql.Rows`, `$1`, `= ANY($1)`, `RETURNING` |
| MySQL 8.4 以上 | `database/sql`（デフォルト、go-sql-driver/mysql 経由） | `*sql.Rows`, `?`, `IN (?, ...)`, `LAST_INSERT_ID()` |

go-sql-driver/mysql が `DATETIME` や `TIMESTAMP` を `time.Time` に読み込むのは、DSN に `parseTime=true` があるときだけなので、アプリが開く DSN にはこれが必要です。ないと、時刻を読むときにそう伝えるエラーを返し、モデルを返す `Insert` は[行を書き込んだあとで](#書き込み)それを返します。さらにドライバは、`loc` で指定したロケーション（指定がなければ UTC）で時刻を書き込み、ゾーンを持たない `DATETIME` をそのロケーションの時刻として読み込みます。データベースを読み書きするすべてのプログラムで同じ `loc` を使い、セッションの `time_zone` で MySQL が変換する `TIMESTAMP` では、`time_zone` も同じゾーンにしてください。

コードはそれぞれ異なり、どれもデータベースを抽象化の裏に隠しません。PostgreSQL と MySQL の違いは、コードを生成する時点で解決されます。

|  | PostgreSQL | MySQL |
|---|---|---|
| 引用符付きの名前 | `"x"` | `` `x` `` |
| パラメータ | `$1`（必要な箇所で再利用） | `?`（使うたびに 1 つ） |
| キーのリスト | `= ANY($1)` | `IN (?, ...)`（長い場合は分割） |
| リレーションのキー | `unnest(...)` を JOIN | `VALUES ROW(...)` を JOIN（長い場合は分割） |
| 書き込みの読み戻し | `RETURNING` | `LAST_INSERT_ID()` とキーによる `SELECT` |
| Upsert | 指定したキーに対する `ON CONFLICT (...)` | 任意の一意キーに対する `ON DUPLICATE KEY UPDATE` |
| 複数行 | `unnest`（1 つの文） | `VALUES`（長い場合は分割） |
| 複数行の COPY | pgx の `CopyFrom` による `COPY`（pgx だけ） | なし |
| キーによるページング | 行の比較（順序の方向が混在する場合を除く） | 展開して書く |

値オブジェクトは `Value` メソッドと `Scan` メソッドを通してデータベースとやり取りし、他の型はドライバが変換するとおりにやり取りします。NULL になりうるカラムはポインタで保持します。database/sql 経由の場合、PostgreSQL の配列をスライスに読み込めるのは Go 1.27 以降で、そこでは pgx/stdlib が各カラムを自分でスキャンします。

## kanna の他のツールとの連携

- [kanna-value](https://github.com/go-kanna/value): 値オブジェクトは `Scan` を通して読み込まれ、`Scan` がルールをチェックします。そのため、データベースにある値をルールが拒否すると、カラムの名前を示すエラーになります。カーソルも同じようにデコードされます。
- [kanna-di](https://github.com/go-kanna/di): `NewOrder` は普通のコンストラクタなので、他のものと同じようにコンテナで提供できます。
- [kanna-fixture](https://github.com/go-kanna/fixture): フィクスチャも普通のモデルなので、`Insert` でテストのデータベースに入れられます。
- [kanna-mapper](https://github.com/go-kanna/mapper): 行はモデルに直接読み込まれるので、マッピングする行の型はありません。モデルからワイヤ型（protobuf などの通信用の型）へのマッピングは、これまでどおり行ってください。

## kanna-orm がしないこと

- 変更の追跡、アイデンティティマップの保持、遅延読み込み。メソッドは、呼ばれたときに、宣言が言う文を実行します。
- ゼロ値をカラムのデフォルト値とみなすこと。ゼロ値は値として書き、データベースが値を割り当てることは `orm:",default"` で言います。
- 任意の JOIN や、サブクエリ・CTE・UNION のようなネストするクエリをスコープから組み立てること。読み取り projection での外部キーによる INNER JOIN と LEFT JOIN、集計の projection のフィールドによるグループ化には対応し、それ以外は[手書きの SQL](#手書きの-sql) を使います。
- 1 つの生成パッケージを PostgreSQL と MySQL の両方で動かすこと。型は、1 つのデータベースが答えたものです。
- マイグレーションの作成や適用。goose などのツールを使い、その結果を `describe` してください。

## まだしないこと

次のものは、今の kanna-orm がしないだけで、しないと決めたものではありません。

- [集計の projection](#集計を読む) の HAVING と、集計の値での並び替え。DTO を返す[手書きの SQL](#手書きの-sql) で書きます。
- リレーションの書き込み。行を参照先と一緒に保存するときの順序は、トランザクションの中で自分で組み立てます。
- NULL になりうるカラムでのページング。
- MariaDB や SQLite のサポート。

## フラグ

```sh
kanna-orm [flags] [packages]
kanna-orm describe [flags] [packages]
kanna-orm vet [flags] [packages]
```

生成:

| フラグ | 意味 |
|---|---|
| `-destination <dir>` | repository の実装を dir に書き出す。インターフェースがある場合は必須。`.` ならインターフェースと同じパッケージに出力する |
| `-driver <name>` | `pgx` または `database/sql`（デフォルト: PostgreSQL では `pgx`、MySQL では `database/sql`） |
| `-snapshot <file>` | 読み込むスナップショット（デフォルト: モジュールのルートの `kanna-orm.snapshot.json`） |
| `-tags <list>` | カンマ区切りのビルドタグ |
| `-check` | 書き出す代わりに、出力が最新であることを検証する。不要な出力が残っていないことも含む |
| `-v` | 書き出した、削除した、変更しなかったファイルを一覧表示する |
| `-version` | バージョンを表示する |

describe:

| フラグ | 意味 |
|---|---|
| `-database-url <url>` | 読み取るデータベース（デフォルト: `$DATABASE_URL`） |
| `-snapshot <file>` | 書き出すスナップショット（デフォルト: モジュールのルートの `kanna-orm.snapshot.json`） |
| `-tags <list>` | カンマ区切りのビルドタグ |
| `-check` | 書き出す代わりに、スナップショットがデータベースに対して最新であることを検証する |
| `-v` | スナップショットを書き出したか、変更しなかったかを表示する |

vet:

| フラグ | 意味 |
|---|---|
| `-tags <list>` | カンマ区切りのビルドタグ |

パッケージのデフォルトはカレントディレクトリのパッケージなので、`//go:generate go tool kanna-orm` に引数は不要です。他の kanna ジェネレータと同じく、`KANNA_CHECK=1 go generate ./...` は書き出す代わりにチェックします。成功した実行は、警告以外何も出力しません。`//kanna:scope` の型も `//kanna:repository` のインターフェースも見つからなかった実行は、そのことを知らせます。宣言がすべてなくなったパッケージの `scopes_gen.go` は削除され、インターフェースがすべてなくなった出力先の `repository_gen.go` も削除されます。ただし、実行時に読み込んだパッケージのコードがその宣言をまだ呼び出している場合は削除されません。同じ名前でも生成コードのヘッダがないファイルには決して触れません。削除を行う `go generate` は `open ...: no such file or directory` で終わります。これは go generate 自身のエラーで、ジェネレータを実行する前にパッケージのファイルを列挙しているためです。ファイルは意図どおり削除されています（[golang/go#36068](https://github.com/golang/go/issues/36068)）。

## サンプル

[`example`](example) は、顧客、商品、注文と、注文の明細、出荷、タグを扱う注文サービスです。pgx 経由の PostgreSQL 向けに [`example/postgres`](example/postgres) に、database/sql 経由の MySQL 向けに [`example/mysql`](example/mysql) に、それぞれ生成しています。1 つのモジュールではテーブルにスコープ型が 1 つなので、それぞれが独立したモジュールです。Go と SQL で書いた独自のスコープ、カーソルによるキーセットページング、各種のリレーション、自然キーによる upsert、複数行の一括書き込み、手書きのクエリ、トランザクションの中での行ロックが含まれます。`make example` は `make db-up` のデータベースをマイグレーションして内容を読み取り、サンプルを再生成し、`kanna-orm vet` で検査して、それぞれに対して実行します。CI も同じことを行い、出力が変わる場合や vet が呼び出しを報告した場合は失敗します。

## 開発

```sh
make test       # unit tests
make db-up      # start the PostgreSQL and the MySQL of compose.yaml, on ports 15432 and 13306
make test-db    # unit tests, and the tests against those databases
make lint       # golangci-lint
make example    # migrate and describe the databases of db-up, regenerate the example, vet it, and run it
make bench      # run the benchmarks in a container next to the PostgreSQL of db-up
```

[`bench/postgres`](bench/postgres/README.ja.md) は、kanna-orm を pgx 単体、sqlc、GORM、bun、ent と比較して計測します。結果と計測方法は、その README にあります。
